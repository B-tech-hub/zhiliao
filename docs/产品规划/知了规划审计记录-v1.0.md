# 知了规划审计记录

版本：v1.0  
日期：2026-08-30  
审计对象：产品调研、产品视觉 PRD、开发实施方案及其与现有仓库的兼容性  
状态：两轮独立审计已完成，规划文档交付通过；实现阻断项另行登记

## 一、审计目标

本记录用于证明本轮规划不是根据竞品列表拍脑袋生成，而是经过代码库调查、GitHub 同类项目调研、产品与视觉审计、第一轮规划审计和第二轮最终交付审计。

审计重点：

1. 是否尊重真实笔记达到 100 条前的新功能冻结。
2. 是否把已经实现、已批准执行和远期候选清楚分开。
3. 是否与 README、CONTEXT、ADR、Issue 计划和源码事实一致。
4. 产品人员能否据此评审定位、用户流程、App 形态和视觉。
5. 开发人员能否据此理解架构、接口、迁移、安全、测试和发布边界。
6. 竞品事实是否有官方来源，是否避免照搬企业平台功能。

## 三、代码库现状审计

代码库审计由独立子 Agent 完成，主 Agent 再以源码交叉核对。

### 3.1 已确认事实

| 领域 | 审计结论 | 规划处理 |
|---|---|---|
| 产品 | 已是可运行的单用户、自托管个人知识库 | 不从零重做，不改成企业平台 |
| 核心流程 | 记录、AI 整理、主题、搜索、来源问答和助手已形成闭环 | 规划聚焦真实使用和可靠交付 |
| App 形态 | 响应式 Web + PWA，可本机或服务器运行 | 明确不是原生或完全离线 App |
| 架构 | Next.js 单体、SQLite WAL、长驻 worker 与调度 | 不部署 serverless，不拆微服务 |
| 数据 | Markdown 持续导出，数据库与图片有每日快照 | 把导出、备份、恢复共同视为信任能力 |
| 外部接入 | `capture:write`、`knowledge:read` 和 MCP 已实现 | 手机捕获首期复用现有接口 |
| 视觉 | 深色左栏、羊皮纸画布、三栏、移动底栏、单一蓝色行动色 | 延续现状，不做彩色后台或营销页 |
| 测试 | 单元与组件覆盖较多，CI 有设计、Lint、测试、构建 | 指出缺少 CI 级浏览器 E2E |

### 3.2 已知缺口

| 缺口 | 证据 | 处理 |
|---|---|---|
| 极短笔记向量误排 | README Roadmap、开发日志真实样本 | 纳入 P0 缺陷，不当作新能力 |
| 大批量导入触发目录扫描阻塞 | 开发日志的 2,000 篇量级实测 | 纳入 P0 性能缺陷 |
| `settings-panel.tsx` 体积过大 | 源码约 1246 行 | 列为维护风险，修改设置页时渐进拆分 |
| 没有事件表和笔记来源字段 | 当前 Schema | 冻结期使用人工/SQL 台账 |
| 缺 CI 级浏览器 E2E | 测试与 CI 目录 | 先保留核心冒烟清单，真实回归驱动立项 |
| `DESIGN.md` 前半与当前 App 不同 | Apple 营销研究与实装附录并存 | 新建 `UI规范.md` 作为唯一执行标准，`DESIGN.md` 降为历史参考 |
| MCP 入口鉴权、工具语义和版本存在偏差 | `src/app/api/mcp/route.ts`、ADR-0019 | 在开发方案登记为实现阻断缺陷，不宣称已修复 |

## 四、第一轮规划审计

第一轮规划审计由独立 `plan_audit` 子 Agent 完成。

### 4.1 阻断项及修正

| 编号 | 审计问题 | 处置结果 |
|---|---|---|
| A1 | 完整交互式首次向导属于新功能，违反冻结 | 已从 P0 移除；冻结期只交付文档决策树、现有提示和空态修正 |

### 4.2 重要修正

| 编号 | 审计问题 | 处置结果 |
|---|---|---|
| B1 | 规划不得另起平行路线 | P0/P1 顺序继承 #4、#10、#5、#8、#9 |
| B2 | “AI 不编造”不能承诺绝对正确 | 改为来源边界可见、引用可核验、来源不足拒答，并要求事实抽查与注入测试 |
| B3 | PWA 能力边界容易被误解 | 明确只有离线兜底，不支持断网记录与同步 |
| B4 | Windows Docker 和主机休眠会影响可用性 | 开发方案增加命名卷、常驻主机和恢复说明 |
| B5 | demo 公开后存在密钥、配置和资源滥用风险 | P0 增加服务端 403、独立卷、mock 模型、限流和重置 |

### 4.3 第一轮结论

修正后，产品定位、App 形态、视觉方向和路线顺序与现有仓库基本一致。以下内容继续保留：

- 单用户、自托管、主题导向。
- 浏览器/PWA 覆盖本机、服务器和手机。
- 真实笔记数作为北极星，100 条前冻结新功能。
- 严格来源边界和 Markdown 数据出口。
- 多用户、SaaS、RBAC、工作流画布、知识图谱和白板明确不做。

### 6.2 可评审性结论

- 产品与设计：PRD 已覆盖定位、用户、App 形态、信息架构、页面规格、视觉 token、状态、指标、路线和验收，可以进入评审。
- 研发：实施方案已覆盖当前架构、部署、数据、迁移、API、安全、测试、发布和文档同步，可以用于拆解已批准工作。
- 竞品调研：未发现会改变路线结论的明显事实错误；活跃度和能力仍按调研日官方资料快照理解，不能代替逐项目部署验证。
- 实现边界：MCP 契约缺陷、极短笔记排序和大批量导入导出阻塞仍是待修代码问题。本轮只交付规划，不以文档修正冒充实现修复。

### 6.3 第二轮结论

原始结论为“有条件通过”。完成 F1、F2、F4 的文档修正并登记 F3 后，规划文档交付通过。通过只表示文档可供产品评审和研发拆解，不表示候选功能已批准，也不表示 MCP 已通过公网安全验收。

## 七、当前审计结论

两轮审计均已完成，规划文档交付通过。后续实施仍受 README 冻结规则、现有 Issue 顺序和 ADR 约束；MCP 入口鉴权与工具语义必须在公开使用前另立缺陷修复并验证。

规划交付后，仓库已补充 `docs/开发规范.md` 与 `docs/UI规范.md`：前者承接日常研发门禁和完成定义，后者成为 App UI 的唯一执行标准。`docs/DESIGN.md` 继续保留为历史视觉研究与实装记录，不再与产品 UI 规范并列。
