# AI 知识库同类产品调研

调研日期：2026-08-30  
调研目标：为知了的产品定位、App 形态、可信问答、部署方式和后续路线提供可核验依据  
调研范围：开源 AI 知识库、RAG 平台、个人第二大脑、local-first 知识工具  
结论置信度：产品与信息架构结论为高；项目活跃度数据为调研日快照，后续会变化

## 一、方法

本次调研由独立子 Agent 完成 16 轮主检索，主 Agent 再完成 12 轮交叉搜索，并读取 8 个关键项目的官方 GitHub README。合计 28 轮搜索，不以二手榜单代替官方证据。

证据优先级：

1. 官方 GitHub README 与仓库元数据。
2. 官方产品文档与部署文档。
3. 搜索结果摘要，仅用于发现候选，不单独作为最终结论。

限制：本轮没有逐个部署竞品，也没有验证其付费版、企业版或路线图中的全部能力。因此“已支持”主要指官方文档明确声明，代码复用和商业能力仍需单独核验。

## 五、市场共性

1. 产品正在从“上传文件后聊天”转向“可维护的知识工作空间”。文档、切片、笔记、引用和版本逐渐成为一等对象。
2. 高质量 RAG 的标准链路已经清楚：解析状态、切片、混合检索、重排、定位引用、反馈和评测。
3. 本机 App 加服务器版的双形态能显著降低理解成本，但维护两套壳也会增加发布成本。
4. Agent、MCP、工作流、定时任务很常见，但它们不是个人知识库最先要证明的价值。
5. 企业产品的门槛已经包含 Workspace、RBAC、SSO、审计和连接器。知了明确不进入该赛道，反而能保持轻量。
6. 知识图谱不是可靠问答的前置条件。更先需要的是稳定记录、可靠搜索、明确来源和可恢复数据。

## 六、知了应借鉴什么

推荐组合：

- 借鉴 AnythingLLM 的安装与上手路径，但保持知了只有主题和笔记两层。
- 借鉴 kotaemon 的引用可见性，但知了首期仍引用真实笔记，不立即扩展 PDF 页码定位。
- 借鉴 RAGFlow 的处理状态和失败恢复思想，但继续使用 SQLite 单体和进程内队列。
- 借鉴 WeKnora 的知识维护观念，但不建设 Workspace、Wiki、图谱和 RBAC。
- 借鉴 Open WebUI 的模型能力提示，但不增加后台式管理复杂度。

## 七、知了不应变成什么

- 不变成企业文档问答平台。
- 不变成可视化 Agent 工作流平台。
- 不变成 Notion、AFFiNE 或 Logseq 的编辑器替代品。
- 不变成多用户 SaaS。
- 不为竞品已有的功能自动立项，所有扩展继续受 100 条真实笔记闸门约束。

## 八、对路线图的影响

### 冻结期 P0

- 保持现有主题、笔记、搜索、未分类、助手和设置结构。
- 优先真实手机捕获、缺陷修复、部署与恢复、公开 demo 安全化、严格来源演示和分发。
- 用文档和现有页面提示降低上手摩擦，不直接新增完整首次向导。

### 证据驱动候选

- 引用原文片段预览。
- PDF 或网页摄取。
- 原生桌面壳或一键本机安装器。
- 本地激活指标与检索质量评测。

这些候选均不是承诺。只有真实使用数据或明确用户反馈证明现有路径不足，才进入 Issue、设计和实施。
