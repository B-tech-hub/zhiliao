## 3. 获准后的串行步骤

### M.1：复核后才允许合并

1. 建立新的仓库外操作记录目录，已存在即换新标识；保存本单/附件哈希、旧证据快照及本地状态。确认本地 HEAD=C、分支正确、暂存区为空，未提交变化只属于已知结果与准备文档；保护旧证据，复核 F 的日志哈希及 C/P/tree 对应关系。
2. 重新查询操作者、仓库配置、Actions、main 规则、PR、候选/main 引用及 F run。要求身份、head/base、检查结果、合并方式、保留分支条件与本单一致。新增规则、拒绝、冲突、UNKNOWN、待审、待检查、自动合并/队列请求或权限不足均停止，不能绕过或改设置。
3. 紧邻合并再次核对 C/B。所有命令检查退出码；401/403、超时或响应不明不当作放行。只读核对可用 `git ls-remote`、`gh pr view 12 --repo B-tech-hub/zhiliao --json headRefOid,baseRefOid,state,mergeable,mergeStateStatus,statusCheckRollup,autoMergeRequest` 和对应 GET API；不运行本机门禁。

### M.2：一次普通 merge

拟用合并标题：`merge: 合入 0.6.1 候选修复、验收与分发准备 (#12)`。

完整正文已准备在 [merge-body.txt](验收证据/r3-gate4-main-preparation-20260930-a/merge-body.txt)，内容及 SHA-256 见 [review.json](验收证据/r3-gate4-main-preparation-20260930-a/review.json)。它概括整个候选及 F 成绩，不预称 main/RC 已通过。使用文件传递多行正文，避免 shell 转义；不另行修改 PR 标题、正文或发评论。

```powershell
gh pr merge 12 --repo B-tech-hub/zhiliao --merge --match-head-commit 41cf296d1d1ccc38d1b2f1b3335cc5b8ac4a4b81 --subject 'merge: 合入 0.6.1 候选修复、验收与分发准备 (#12)' --body-file 'docs/验收证据/r3-gate4-main-preparation-20260930-a/merge-body.txt'
```

仅执行一次；不加 `--admin`、`--auto`、`--delete-branch`，不直接 push main。仓库自动删分支必须仍关闭。`--match-head-commit` 只原子约束 head，**不锁定 base**；前后核对可以发现竞态，不能承诺阻止它。若合并请求超时、非零或状态不明，保存输出，只读查询 PR/refs/Actions；不再次发送合并请求。若确认合并已经发生，继续取证并监控已启动 CI，不回滚 main。

### M.3：识别实际合并提交

查询 PR 的 merged 状态、mergeCommit、mergedAt、mergedBy，读取 M 的 commit API 与远端引用。必须同时满足：

- PR #12 已合并到 main，候选分支仍指向 C；远端 main=M。
- M 恰有两个 parents，依次为 `[B, C]`；`tree(M)=T`。不以 PR 事后 merge ref 替代 M。
- 留存 M 的作者、提交者、签名/verification、API 用户身份以及合并操作者，不假定其等于本机 Git 身份。
- 若 main 前进、parents/tree 不符或出现额外提交，标记 M 未通过并停止后续动作；已经发生的合并如实保留，不自动回滚或修改批准值。

### M.4：观察自动 main CI

现有 `.github/workflows/ci.yml` 对 main push 自动触发：Ubuntu 托管 runner、Node 22、npm cache、`npm ci`、版本检查、设计、lint、`REQUIRE_DOCKER_COMPOSE=1` 全量测试、build/TypeScript。M 授权必须包括这次完整 CI。保持原工作流，不手动 dispatch/rerun，不关闭触发器，不再跑本机完整门禁。

按实际 M 查询，分页取全；下面 `$mergeSha` 必须是经过 M.3 核对的真实 M：

```powershell
gh api --paginate --slurp "repos/B-tech-hub/zhiliao/actions/runs?head_sha=$mergeSha&per_page=100"
```

要求唯一目标为 `ci.yml`、`push`、main、head_sha=M、attempt 1、正确仓库及操作者，并在完整日志中取得实际 checkout=M。PR CI 成功或只看 head_sha 都不能替代这一步。记录实际 runner/image、Node/npm、缓存命中与耗时；版本可能与 F 的补丁号不同，不预填沿用 F 环境。

无 run 时只读观察最多 10 分钟，不补触发；发现重复 run、意外 Release、解析失败、等待权限或身份不符即停止后续阶段。对本次新 M 上正在运行的意外工作流可按下节定向取消；不得取消历史或其他提交的 run。已知发布工作流只由版本 tag 触发，但仍查询 M 上全部工作流，不能只凭过滤器断言不会有失败记录。

## 4. 资源、时限与停止条件

| 项目 | 范围 |
|---|---|
| 人员 / 平台 | 单 Agent；现有标准 GitHub 托管 Ubuntu runner，不启用 larger runner、扩容或本机代跑 |
| 运行次数 | 一次合并产生的一轮自动 main CI；不重复合并、推送、rerun 或补提交 |
| run 出现 / 排队 | 合并后最多 10 分钟等待 run；目标 run 连续排队最多 30 分钟 |
| job 运行 | 最多 60 分钟；CI 无显式 job timeout，这是人工监控上限 |
| 总墙钟 | 从合并请求起最多 100 分钟，包含等待 run 与排队；取证归档另计 |
| 资源限制 | 使用现有 runner 的 CPU/内存/磁盘；记录实际值，不声称 CI 已配置额外硬配额；额度/策略阻止时停止，不充值 |
| 观察间隔 | 30–60 秒一次定向只读查询 |

失败、超时、取消、身份漂移、缺证、测试异常跳过或构建未执行，均不能判定 M 通过。遇超限或意外正在运行的工作流，定向执行 `gh run cancel <本次已核对run-id> --repo B-tech-hub/zhiliao`，随后只读确认终态；取消命令成功不等于已停止。取消失败或仍运行时如实标明，保持观察，不自动使用 force-cancel、修改工作流或扩大权限。

保留首次失败与残留远端状态，不自动修复、回滚 main 或放宽断言。M 可能已合并但 CI 失败，这时只完成合并事实，R 仍停止。28 项既有条件跳过须逐项解释；测试数量与 F 不同先调查，不预填 884 或把 skip 算作通过。
