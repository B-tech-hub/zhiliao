# 知了项目开发规范

版本：v1.0  
日期：2026-08-30  
适用范围：知了 v0.6.0 及后续迭代  
状态：项目级执行规范

## 一、目的与适用范围

本规范用于约束需求分析、代码实现、验证、文档和交付，防止后续开发偏离“记、找、用”的产品主线，或破坏已经形成的数据、安全和交互契约。

本规范不替代产品规划、领域术语和 ADR。它回答的是“一个已经批准的改动应当怎样开发”，不自动授权任何候选功能。

适用于：

- Next.js 页面、Route Handler 和服务端逻辑。
- React 组件、编辑器、助手和交互层。
- SQLite Schema、迁移、搜索、AI 队列和数据生命周期。
- Docker、PWA、外部 API、MCP、备份和发布流程。
- 测试、文档、Issue、PR 和 Agent 协作。

## 二、事实来源与冲突处理

发生冲突时按以下优先级处理：

1. `README.md` Roadmap、用户明确批准的当前任务和冻结规则。
2. `CONTEXT.md` 中的领域语言与产品不变量。
3. 已采纳的 `docs/adr/` 架构决策。
4. 当前 Issue、`docs/Issue执行计划-2026-08-29.md` 和已批准验收标准。
5. `docs/产品规划/知了产品视觉PRD-v1.0.md` 与开发实施方案。
6. 本开发规范和 `docs/UI规范.md`。
7. 当前源码、测试和运行证据。

源码是现状事实，但不自动高于已批准决策。发现源码与规范不一致时，应区分：

- 文档过期：同步修正文档。
- 实现缺陷：按缺陷流程修复并补回归测试。
- 历史兼容：登记例外，不在无关任务中扩大或顺手重写。
- 决策变化：新增 ADR，不得静默覆盖旧决策。

## 三、需求与立项门禁

### 3.1 先判断改动类型

开始实现前必须把任务归入以下一种类型：

| 类型 | 例子 | 冻结期处理 |
|---|---|---|
| 缺陷修复 | 数据丢失、错误状态、性能退化、契约偏差 | 可推进，必须有复现与回归 |
| 文档 | 安装、接口、恢复、使用说明 | 可推进，需核对源码事实 |
| 分发与运维 | Docker、demo 隔离、发布、监控 | 可推进，安全边界必须在服务端生效 |
| 内部重构 | 拆分大组件、去重、提高可测试性 | 仅在服务当前批准任务时推进，不得改变语义 |
| 新功能 | 新页面、新入口、新状态、新数据类型 | 默认冻结，需明确批准或例外决策 |

### 3.2 以下变化默认视为新功能

- 新增一级导航、独立页面或持久化向导。
- 新增数据表、用户行为事件、长期保存的偏好或内容类型。
- 新增外部 API、Token 作用域或 AI 工具。
- 新增 PDF、网页、音视频等摄取类型。
- 新增账号、成员、Workspace、权限或协作概念。
- 改变来源问答边界、数据导出承诺或离线能力口径。

### 3.3 批准后的任务说明至少包含

- 当前问题和可复现证据。
- 本次范围与明确非目标。
- 涉及模块、数据、接口、页面和文档。
- 失败、回退和兼容风险。
- 可观察、可复核的验收标准。

不得用“顺便优化”“竞品都有”“以后可能需要”扩大范围。

## 四、标准开发流程

### 4.1 调查

1. 阅读相关产品文档、领域术语、ADR 和现有 Issue。
2. 使用 `rg` 查找真实入口、调用链、测试和文档引用。
3. 检查工作区状态，保留用户已有修改。
4. 找到成功路径、失败路径、降级路径和数据写入路径。
5. 优先复用已有测试、日志、截图和真实样本。

### 4.2 计划

中等及以上复杂任务在实现前说明：

- 当前理解。
- 实施步骤。
- 影响范围。
- 主要风险。
- 验收标准。

计划与实现分开汇报。关键未知项必须明确列出，不用猜测替代事实。

### 4.3 实现

- 一个改动只解决一个明确问题。
- 沿用现有框架、模块和辅助函数，不平行发明第二套路径。
- 先修改最靠近责任归属的模块，再修改调用方。
- 不在功能修复中夹带全局格式化、依赖升级或目录重组。
- 复杂逻辑先保证边界与失败语义，再考虑抽象。

### 4.4 验证

- 先运行最小相关测试或局部检查。
- 涉及真实浏览器、模型、Docker、网络或恢复时，保留人工步骤和证据。
- 完整门禁只在合并、发布或用户批准后运行。
- 验证失败必须区分代码失败、环境失败和既有失败。

### 4.5 交付

- 先给结果，再说明关键实现与验证。
- 明确未运行的验证及其残余风险。
- 同步接口、部署、页面行为、ADR、README、CHANGELOG 等相关文档。

## 五、技术与架构基线

| 层级 | 基线 | 不得偏离 |
|---|---|---|
| 应用 | Next.js 15 App Router、React 19、TypeScript | 不拆独立后端或微服务 |
| 样式 | Tailwind CSS 4、项目语义 token | 不建立平行主题系统 |
| 数据 | Drizzle、better-sqlite3、SQLite WAL | 不做多实例并发写入 |
| 异步任务 | SQLite 持久化任务表、进程内 worker | 不部署到 serverless |
| 搜索 | FTS5、jieba、Embedding、RRF | Embedding 不可用时必须降级 BM25 |
| 编辑与出口 | TipTap、Markdown、增量导出 | 不把数据锁死在数据库中 |
| 分发 | Docker、GHCR、响应式 Web、PWA | 不宣称原生或完全离线 App |

启动流程依赖长驻 Node.js 进程。任何部署和重构都必须保留 AI worker、备份和每周回顾调度的持续运行能力。

## 六、目录与责任边界

| 目录或模块 | 责任 | 规则 |
|---|---|---|
| `src/app/` | 页面、布局、Route Handler | 页面取数优先服务端；边界输入必须校验 |
| `src/components/` | 可复用交互与展示组件 | 遵守 UI、焦点和响应式契约 |
| `src/db/` | Schema、单连接、内嵌迁移 | 迁移只追加，不改写历史 |
| `src/lib/note-write.ts` | 笔记新建、更新、导入和恢复 | 笔记写入不得绕过该层 |
| `src/lib/ai/` | AI 处理、对话、工具和调度 | 失败不得破坏基础记录与检索 |
| `src/lib/search.ts` | FTS、向量和融合排序 | 向量失效时保留可解释降级 |
| `src/lib/markdown-export.ts` | 持续 Markdown 导出 | 不得阻塞请求主路径 |
| `src/lib/backup.ts` | 数据库与图片快照 | 备份成功后才允许破坏性清扫 |
| `tests/` | 单元、组件、API 和验收样本 | 测试数据与正式数据完全隔离 |

`settings-panel.tsx` 是已知大组件。修改设置页时可按现有分区渐进拆分，但不得借拆分改变业务语义或导航结构。

## 七、代码通用约定

### 7.1 编码与格式

- 文件使用 UTF-8、LF，遵守 `.gitattributes`。
- 代码注释使用简体中文，优先使用 GB2312 常用字符；注释说明原因、约束和陷阱，不复述代码。
- TypeScript 保持 `strict: true`，不得通过关闭规则绕过类型问题。
- 使用 `@/` 路径别名引用 `src/` 内模块。
- 不做与任务无关的全文件重排和格式噪音。

### 7.2 命名

| 对象 | 规则 | 示例 |
|---|---|---|
| 文件 | 小写 kebab-case | `note-write.ts` |
| React 组件、类型、类 | PascalCase | `QuickCapture` |
| 函数、变量 | camelCase | `createNote` |
| 常量 | UPPER_SNAKE_CASE 或语义常量对象 | `INBOX_TOPIC_ID` |
| 布尔值 | 使用 `is/has/can/should` 前缀 | `isLlmConfigured` |
| 事件 | 动作或状态变化语义 | `toggleChat`、`quickCapture` |

命名应使用 `CONTEXT.md` 中的领域语言，不另造“文件夹”“空间”“知识条目”等平行概念替代主题和笔记。

### 7.3 类型与边界

- 外部输入、请求体、模型结构化输出优先用 Zod 校验。
- 禁止无范围的 `any`、`@ts-ignore` 和宽泛类型断言。
- 原生库或第三方类型确有缺口时，可使用最小范围断言，并用中文注释解释原因。
- 错误类型应携带调用方需要判断的稳定 code，不依赖错误文本分支。
- 公共函数输入输出使用显式类型；局部简单值允许推断。

### 7.4 函数与抽象

- 一个函数负责一个可命名的业务动作。
- 跨表一致性、写后副作用和安全边界集中在领域函数中，不散落在 Route Handler。
- 只有在消除真实重复、隔离风险或匹配既有模式时才增加抽象。
- 不为单一调用点提前建设通用框架。

## 八、Next.js 与 React 约定

- Server Component 为默认选择；只有事件、浏览器 API、局部状态或 effect 需要时才使用 `"use client"`。
- 页面和布局负责取数与组合，复杂业务写入放到 `src/lib/`。
- 不在客户端暴露 API Key、数据库配置、内部路径或服务端错误堆栈。
- 响应式优先使用 CSS 断点，避免依赖 JS 媒体查询造成首帧和水合抖动。
- 请求 effect 必须处理卸载、竞态和过期响应；可取消请求使用 `AbortController`。
- 用户输入在网络失败时应保留，后台辅助失败不得清空正文或阻断保存。
- 全局快捷键必须给编辑器和普通输入框让路。

页面和组件的视觉、键盘、焦点、状态与响应式规则见 [UI 规范](UI规范.md)。

## 九、API 与服务端边界

### 9.1 输入和响应

- Route Handler 在读取业务数据前完成鉴权和参数校验。
- JSON 请求使用 Zod 或等价结构化校验，不手写脆弱字符串解析。
- 成功状态使用符合语义的 `200`、`201` 或无内容响应。
- 常用错误码口径：

| 状态码 | 用途 |
|---:|---|
| 400 | 参数错误、业务前置条件不满足 |
| 401 | 未登录、Token 无效或缺失 |
| 403 | 已识别身份但禁止当前能力，例如 demo 限制 |
| 404 | 对象不存在或已不可访问 |
| 409 | 状态冲突、重复资源、乐观锁失败 |
| 429 | 限流 |
| 500 | 未预期服务端失败 |
| 503 | 依赖或健康检查不可用 |

- 用户可见错误使用简体中文，说明发生了什么和下一步；外部标准协议按协议要求保留英文错误。
- 不把数据库异常、路径、密钥或第三方完整响应直接返回客户端。

### 9.2 鉴权与权限

- 浏览器页面使用签名会话；外部 API 使用最小作用域 Bearer Token。
- `capture:write` 与 `knowledge:read` 不得混用。
- 前端隐藏不是安全边界，禁止能力必须由服务端返回 403 或等价拒绝。
- Token 明文只在创建时显示一次；数据库只存哈希，日志和测试夹具不得出现真实值。
- MCP 公网使用前必须完成入口鉴权和工具语义一致性修复。

### 9.3 外部请求

- 所有模型、抓取和外部服务请求设置超时并支持中断。
- `fetch_url` 只能访问用户明确提供的 URL，并继续遵守 SSRF 防护。
- 对请求体、图片数量、文件大小、像素数和工具调用轮数设置服务端上限。
- 第三方失败应转换为稳定、可操作的产品状态。

## 十、数据、迁移与生命周期

### 10.1 迁移

1. Schema 变化同时更新 `src/db/schema.ts` 和 `src/db/migrations.ts`。
2. 迁移 ID 只追加，已发布迁移不得修改、重排或复用。
3. 每个迁移在事务中完成，并使用旧库副本验证升级。
4. 删除列、重建表和批量回填前必须有备份、耗时评估和回退方案。
5. 迁移失败不得留下“应用已启动但数据只改一半”的状态。

### 10.2 笔记写入

新建、更新、导入和助手写操作必须复用 `src/lib/note-write.ts` 或其明确扩展，统一处理：

- FTS 同步。
- AI 状态和任务入队。
- 标题、主题、标签锁字段。
- Embedding 与分块失效。
- Markdown 增量导出。
- 用户纠正学习记录。

不得在 Route Handler、组件或 AI 工具中直接写 `notes` 后遗漏这些副作用。

### 10.3 删除、导出与恢复

- 普通删除进入回收站，不得直接物理删除。
- 彻底删除和自动清扫必须遵守“先备份成功，再销毁”。
- 回收站笔记不参与列表、搜索、计数和 AI 队列。
- 导入、恢复和覆盖写入必须清理旧向量、旧分块和旧导出路径。
- 备份成功不等于可恢复，发布和重大迁移需完成真实恢复演练。

## 十一、AI、搜索与工具调用

- 文本模型未配置或失败时，笔记仍必须可以保存、编辑、搜索和导出。
- Embedding 未配置、失败、维度变化或向量过期时自动降级 BM25。
- AI 整理不得覆盖用户锁定的标题、主题和标签。
- AI 工具不存在覆盖正文能力；写操作留下操作卡片并可撤销，删除前必须确认。
- 来源问答只能依据来源集，资料不足是正常完成状态，不触发编造或无限重试。
- 引用链接只允许使用真实工具返回或来源集中存在的笔记 ID。
- 思考过程可保存展示，但不得回灌后续模型上下文或写入普通笔记。
- 辅助能力失败必须与核心写作路径隔离，例如相关笔记和冲突判断失败不影响保存。
- 新增模型调用需明确成本上限、超时、重试、降级、数据发送范围和测试方式。

## 十二、错误、日志与可观察性

- 预期业务错误使用稳定错误类型或结果对象，不滥用异常控制正常流程。
- 异步任务日志包含模块、任务 ID、尝试次数和最终状态，但不记录正文、API Key、Token 或完整模型输入。
- 可重试错误使用有限次数和退避；不可重试错误直接进入可见失败状态。
- `console.log/warn/error` 仅用于服务端生命周期、任务和故障信息，客户端不遗留调试输出。
- 错误提示区分用户可处理问题、配置问题、第三方失败和内部错误。

## 十三、性能与资源约束

- 不在请求主路径执行全库递归扫描、批量向量计算或大文件同步处理。
- 大批量导入导出必须记录规模、耗时和事件循环影响，至少覆盖既有 2,000/5,000 篇样本要求。
- 搜索、命令面板和相关笔记请求使用防抖，并取消过期请求。
- 图片处理设置文件、像素、单次数量和总载荷上限。
- 不为未来水平扩展提前拆服务；先在 SQLite 单实例边界内解决真实瓶颈。

## 十四、测试与验证

### 14.1 分层原则

| 变更类型 | 最小验证 | 合并或发布前补充 |
|---|---|---|
| 纯函数、领域逻辑 | 对应 Vitest 文件 | 相关测试集 |
| API | Route/lib 测试，覆盖成功和主要错误码 | 真实 HTTP 冒烟与文档示例 |
| 数据迁移 | 旧库副本升级、数据计数和字段核对 | 隔离容器升级与恢复 |
| 搜索 | 固定正反例、降级和向量过期 | 真实模型样本与延迟记录 |
| AI 工具、来源问答 | 权限、边界、注入、引用和撤销测试 | 真实模型人工抽查 |
| UI | 组件测试、键盘、焦点、响应式检查 | 桌面/手机、浅色/深色截图 |
| Docker/PWA | 健康检查、卷持久化、HTTPS | Windows/Linux 与蜂窝网络 |
| 备份恢复 | 快照完整性和 WAL 处理 | 真正恢复并打开笔记与图片 |

### 14.2 执行约束

- 默认先运行与改动文件直接相关的测试。
- 不为了“看起来更完整”重复运行已有且仍有效的重验证。
- `build`、全量测试、真机和重型浏览器验证先说明必要性并获得确认。
- 正式合并或发布前完整门禁为：

```bash
npm run check:design
npm run lint
npm test
npm run build
```

- 当前没有 CI 级浏览器 E2E。涉及核心页面时必须保留可重复的浏览器冒烟步骤；回归频繁后再单独立项引入少量核心 E2E。

## 十五、安全基线

- 正式环境必须配置强 `APP_PASSWORD` 和 `SESSION_SECRET`，不得使用示例值。
- `.env`、数据库、上传、备份和日志不得提交仓库。
- 正式、demo、测试和验收实例使用不同数据库、目录、卷、项目名和密钥。
- demo 只使用 mock 模型，不允许创建 Token、下载备份、导入或触发高成本操作。
- 路径、文件名、压缩包和 URL 均视为不可信输入。
- 恢复、导入和迁移在隔离副本验证后才接触正式数据。
- 对外文档和截图不得包含真实域名后台、Token、Key、内部 IP 或用户笔记。

## 十六、文档同步矩阵

| 变化类型 | 必须同步 |
|---|---|
| 产品范围、导航、核心流程 | 产品视觉 PRD、README、Issue 或 ADR |
| 页面行为、组件或视觉 token | `docs/UI规范.md`、产品视觉 PRD、设计门禁 |
| 外部 API、Token、错误码 | 开发实施方案、ADR-0019、调用指南、测试 |
| 数据表、迁移、生命周期 | Schema、迁移、ADR、备份恢复、升级说明 |
| 搜索、向量、分块 | ADR-0018/0023、README、验收样本 |
| 导入导出 | ADR-0020/0024、README、迁移和恢复说明 |

## 十七、Git、Issue 与 PR

- 较大改动先关联 Issue；一个 PR 只解决一个主题。
- PR 标题使用 `feat:`、`fix:`、`docs:`、`refactor:`、`test:`、`chore:` 前缀。
- 提交和 PR 描述优先使用中文，命令、API 和文件名保留英文。
- UI 变化附桌面/移动、必要的浅色/深色截图。
- 行为变化写出复现、验证、回退和文档同步情况。
- 数据库变化明确列出新增迁移 ID 和旧库升级证据。
- 不回退或覆盖工作区中与任务无关的已有修改。

## 十八、开发完成定义

一个批准后的改动只有同时满足以下条件才算完成：

1. 问题、范围、非目标和验收标准明确。
2. 未违反新功能冻结和产品不变量。
3. 实现沿用现有模块边界，没有第二套写入、主题或设计系统。
4. 输入、权限、安全和失败路径在服务端生效。
5. 数据迁移、回退、降级和恢复风险得到处理。
6. 最小相关测试通过，必要时有浏览器、真机或恢复证据。
7. API、部署、视觉、ADR、README 和发布文档按矩阵同步。
8. 没有混入无关重构、依赖升级或格式化噪音。
9. 未执行的验证和剩余风险已明确交付。

## 十九、例外管理

规范例外必须满足：

- 有具体文件、代码行或场景范围。
- 有不能立即修复的技术原因。
- 不把整文件或整目录加入宽泛白名单。
- 新代码不得复制例外。
- 条件成熟时以独立任务移除。

当前已知例外包括 Mermaid NodeView 的精确圆角行、部分第三方类型断言和现有 UI 任意字阶。例外是兼容债务，不是新代码模板。
