## 2. 排期原则（沿用意图文档 §9）

**按「越晚做越贵」排，不按「想做什么」排。**

这一轮的判据比上一轮更细一层：上一轮识别出「embedding 列」是唯一随笔记数增长而变贵的改动，这一轮要识别出**还有哪些改动会触发全量回填**。

| 任务 | 是否触发全量回填 | 成本是否随时间增长 |
|---|---|---|
| 真实供应商实测 | 否 | 否，但**阻塞对其余任务的判断** |
| 长笔记分块 | **是**（向量粒度改变，全部重算） | **是** |
| AI 查询改写 | 否（只在读取时多一次 chat 调用） | 否 |
| 首页进/出指标 | 否（新增事件表，历史无数据可补） | 否 |
| 「这条还成立吗」回顾 | 否 | 否 |

结论：**T0 实测 → T1 分块 → T2 查询改写 → T3/T4 出口件**。

分块必须排在查询改写之前，否则先做查询改写、再做分块时仍要回填一次，而那时笔记更多、更贵。查询改写不碰存储，晚做成本不变。

## 3. T0 · 真实供应商实测（阻塞项，最高优先）

### 为什么它是一个任务，而不是一个步骤

P0-1 的代码完成度不等于验收达成。意图文档 §3 给 P0-1 定的验收信号是：

> 用口语化转述能召回原意不同的笔记（例：查「拖延」应召回正文写作「又摸鱼了一下午」的笔记）

这条此前**没有被写进受版本控制的开发日志，也没有用用户真实笔记样本完成验收**。后续调查找到一份旧隔离验收交接：自定义网关曾用 6 条预备笔记跑过 10 组查询，其中 `Qwen/Qwen3-Embedding-4B` 为 10/10、当前选择的 8B 为 8/10；但它没有记录真实回填耗时、token 或每千条成本，而且当前端点已无法复测。因此这份记录只能证明「供应商曾可用」，不能替代本节的最终验收。

而开发日志自己记着一条元教训（第 342 行）：

> mock LLM 与打桩 DNS 验证不了真实网络，这类缺陷只有接上真实模型、在真实机器上跑才会显形。

在未验证的地基上加分块和查询改写，是把两层新逻辑压在一个未知之上。

### 阻塞条件

**需要一组当前可达、支持 OpenAI 兼容 `/embeddings` 的供应商配置。** 旧隔离库中的 Key 仍在，但对应网关当前被 Cloudflare 403 拒绝，不能继续充当验收端点。可换用通义 `text-embedding-v3`、智谱 `embedding-3`、硅基流动 `bge-large-zh` 等中文优先模型；配置继续只写本地 `.env.local` 或隔离实例设置页，不进入对话、仓库、日志或交接文档。

### 步骤

1. 隔离环境执行 `node verify-embedding.mjs`，确认接口形态、返回维度、中文语义区分度
2. 在隔离实例（非正式库）配置三项，测试连接，确认落库的 `embedding_model` 与真实产出方一致（ADR 0018 记过一次「只填模型名、baseUrl 静默兜底到别处」的踩坑）
3. 由用户从真实笔记中挑选验收样本：至少 5–10 组「措辞完全不同但语义相近」的笔记/查询对，含意图文档点名的「拖延 / 又摸鱼了一下午」
4. 执行补算，记录耗时与 token 消耗（作为分块任务的成本基线）
5. 逐条验证召回，记录 `vectorEnabled`、命中位次
6. 故障注入：换模型名后确认 `staleEmbeddingCount` 正确计数、搜索降级为 BM25 不报错

### 验收标准

- 10 组样本中至少 8 组在前 10 位召回（低于此比例应先怀疑供应商/模型选择，而非急着加分块）
- 换模型后有明确提示、无静默错误结果
- 供应商断连时搜索仍可用，日志有 `console.warn` 留痕
- 结果写入 `docs/开发日志.md`，含实际维度、耗时、每千条成本
- **延迟分布（2026-08-26 补充）**：单条查询 embedding 的中位延迟需在 1.5 s 内，且必须**跨时间多轮采样**后再下结论。首轮实测曾出现中位 8.4 s、尾部 17.3 s，据此差点误判供应商不可用；后续多轮稳定在 0.85–1.4 s，证明那是共享推理服务的间歇性负载。对这类服务，单轮连续采样会把一次高峰当成稳定特征
- **尾部延迟的工程约束**：尾部慢请求真实存在，`/api/notes/[id]/related` 由打字停顿触发，高峰期会堆积在飞请求。实现时除防抖外还需并发闸门（同一笔记只保留最后一次请求）

### 风险

- **样本自造有确认偏差**：由我造样本、我验证，容易挑对模型友好的例子。建议由你从自己真实笔记里挑几条，用你当时会用的措辞去搜
- 若召回率不达标，需要先调 `buildNoteEmbeddingText` 的拼接方式或换模型，**这属于 T0 范围内的迭代，不应带着不达标的基线进 T1**

## 4. T1 · 长笔记分块（chunking）

### 问题

当前 `buildNoteEmbeddingText`（`src/lib/ai/embedding.ts:10`）把「标题 + 摘要 + 正文」拼成一段、截断到 5000 字，整条笔记只产出**一个**向量。后果是 ADR 0018 自己写下的：

> 长笔记的单一向量会稀释语义、末尾内容召回率偏低。

一篇 3000 字的笔记里，末尾那段结论会被前面 2500 字摊薄；而超过 5000 字的部分**根本没进过向量**。

### 方案

新增 `note_chunks` 表，把向量从「一条笔记一个」改为「一条笔记多块」：

```sql
-- 迁移 0014_note_chunks
CREATE TABLE IF NOT EXISTS note_chunks (
  id TEXT PRIMARY KEY,
  note_id TEXT NOT NULL,
  chunk_index INTEGER NOT NULL,
  text TEXT NOT NULL,
  embedding BLOB,
  embedding_model TEXT,
  embedding_dim INTEGER,
  embedding_updated_at INTEGER
);
CREATE INDEX IF NOT EXISTS idx_note_chunks_note ON note_chunks(note_id, chunk_index);
```

要点：

- **分块策略**：优先按 Markdown 结构切（`##` 标题、空行段落），再按字数上限兜底。不做固定窗口滑动切分——笔记大多有结构，按结构切能保住语义完整性
- **保留 `notes.embedding`**：短笔记（单块）仍走原列，`note_chunks` 只为多块笔记服务。这样绝大多数笔记不产生额外行，也不必推翻已实测通过的路径
- **检索侧**：`vectorSearch` 改为同时扫两处，按 `note_id` 取该笔记所有块的**最高分**作为笔记得分（max-pooling，不做平均——平均会让长笔记再次被稀释，等于白分块）
- **陈旧判定沿用现有逻辑**：模型名与维度必须同时对上，否则计入 `staleEmbeddingCount`

### 影响范围

| 文件 | 改动 |
|---|---|
| `src/db/migrations.ts` | 新增 0014 迁移 |
| `src/db/schema.ts` | 新增 `noteChunks` 表定义 |
| `src/lib/ai/embedding.ts` | 新增分块函数；`buildNoteEmbeddingText` 保留给单块路径 |
| `src/lib/ai/worker.ts` | `embed_note` 分支改为写多块；幂等检查需按块判断 |
| `src/lib/search.ts` | `vectorSearch` 扫描范围与 max-pooling |
| `src/lib/trash.ts` / 清扫链路 | 笔记彻底删除时必须连带删块（**易漏**） |
| `/api/embedding/backfill` | 待补算计数逻辑改变 |

### 风险

- **请求量倍增**：一条长笔记从 1 次请求变成 N 次。T0 记录的成本基线在这里被放大，需重新估算并确认供应商速率限制。`embedTexts` 已有 `BATCH_SIZE = 64` 批量能力可复用
- **孤儿数据**：这是本任务最可能留下的隐患。项目已在 HEIC（ADR 0014）踩过「四条链路要成对处理」的坑，分块同理——删除、回收站清扫、备份、导出四处都要确认
- **max-pooling 可能让短笔记吃亏**：单块笔记的整体相似度 vs 长笔记某一块的局部高相似度，不完全可比。需在 T0 的样本集上回归验证，确认分块**没有让原本召回正常的短笔记掉出前 10**

### 验收标准

- T0 的 10 组样本回归不退化
- 新增长笔记样本（>3000 字、结论在末尾）能被针对末尾内容的查询召回——这是分块存在的唯一理由，必须单独验证
- 彻底删除一条多块笔记后，`note_chunks` 无残留（写成自动化测试，别靠手查）

> **2026-08-27 实测更正**：本节原有一条判据「T0 第 8 条应从第 3 上升」已作废——该条在纯向量侧一直是 Top1，排第 3 是 BM25 经 RRF 融合导致，与向量稀释无关。上面第二条的验证方式也要改：**必须直接测 `vectorSearch`**，测 `hybridSearchNoteIds` 时 BM25 索引全文、不受 5000 字截断影响，会让对照组也通过，测出的是「系统鲁棒」而非「分块有效」。

## 5. T2 · AI 查询改写（已放弃，2026-08-27）

> **本任务按本节自己写下的放弃条件放弃。** 下面的验收标准要求「至少 3 组 BM25 与向量都召不回、改写后能召回的样本，若找不到应当放弃本任务」。实测查清：正式库只有 **7 条笔记且全是测试数据**（最长 3985 字，另有一条正文仅 2 字）。**候选池 7 条，从 7 条里选 Top3 几乎必中，结构上产生不了这种样本**；人为构造只是合成样本，证不了真实价值。
>
> 这不否定 T0/T1——地基的逻辑是「越晚做越贵」，只有 7 条时补算成本约等于零，正是做地基的最佳时机；而 T2 属于优化，晚做不会变贵，随时可以重启。
>
> **重启条件**：真实笔记达到百条量级后重新找样本再评估。届时下面的方案与约束仍然有效，尤其是「`/related` 绝对不能改写」这条硬约束。

### 关键约束（先看这条，它决定了实现形态）

`hybridSearchNoteIds` 目前有 4 个调用点，语境完全不同：

| 调用点 | 传入的 query | 触发方式 | 适合改写？ |
|---|---|---|---|
| `/api/search` | 用户输入的搜索词 | 用户主动、低频 | ✅ 正是目标场景 |
| `src/lib/ai/tools/search-notes.ts` | 模型自己生成的查询 | 助手工具调用 | ⚠️ 模型已在循环里，再套一层改写是双重推理 |
| `/api/external/knowledge` | 外部/MCP 传入 | 外部调用，可能高频 | ⚠️ 应由调用方显式开启 |
| `/api/notes/[id]/related` | **正文前 2000 字** | 打字停顿 900ms 自动触发 | ❌ **绝对不能** |

最后一行是硬约束：`/related` 传的不是查询而是长文本，且由打字停顿自动触发。若把改写做进 `hybridSearchNoteIds` 内部，用户每写几句话就会烧一次 chat 调用去「改写」一篇正文——这正是意图文档 §2.1 批评的「每条笔记必调一次主力模型」的成本焦虑，会在读取侧原样重演。

**因此：改写必须是显式开启的选项，默认关闭，不得默认注入。**

### 方案

```ts
// src/lib/search.ts
export interface HybridSearchOptions {
  limit?: number;
  allowedIds?: Set<string>;
  rewrite?: boolean;   // 默认 false，只有 /api/search 传 true
}
```

- 改写产出**同义查询数组**（原查询 + 最多 2 条改写），各自跑一遍 BM25 与向量召回，全部结果一起进 RRF。原查询的排名权重不低于改写结果——改写是补充召回，不是替换
- 走 chat 模型，`temperature` 低、`max_tokens` 小（改写只需几十 token），超时短（3 秒），**失败即静默跳过**，退回两路
- 只在查询「像自然语言」时触发：长度 ≥ 6 字或分词后 ≥ 3 词。单词查询（「羽毛球」）BM25 已经够，不值得多花一次调用
- 结果缓存：同一查询串在进程内缓存 5 分钟，避免用户翻页/微调重复烧钱

### 影响范围

`src/lib/search.ts`、`src/app/api/search/route.ts`、新增 `src/lib/ai/query-rewrite.ts`、设置页开关（默认关闭）。**不动** `/related` 与 `search-notes.ts`。

### 风险

- **成本回到「贵」的那一档**：意图文档 §8 开放问题 5 已经点明，chat 模型的成本量级与 embedding 相差约两个数量级。这也是它必须默认关闭、必须有触发门槛的原因
- **改写可能引入噪声**：模型把「拖延」改写成「时间管理」「效率」，召回一堆无关笔记。缓解手段是 RRF 里原查询权重优先 + 改写数量封顶 2 条
- 必须验证的反例：**开启改写后，原本召回正确的查询不能变差**

### 验收标准

- T0/T1 样本集在开启改写后不退化（这是底线）
- 至少 3 组「BM25 与向量都召不回、改写后能召回」的样本，证明这一路有独立价值。**若找不到这样的样本，应当放弃本任务**而不是硬上——三路融合是手段，不是目的
- 关闭开关后，代码路径与当前完全一致（无残留调用）
- `/related` 路径确认零 chat 调用（打字时观察日志）

## 6. T3 / T4 · 出口三件套的剩余两件

### T3 · 首页进/出指标

意图文档 §4：把「共 800 条笔记」改成「本周进 12 条／出 3 条」，让「用了多少」可见而非「存了多少」可见。

**核心未决问题：「出」如何定义？** 目前数据库里**没有任何表记录笔记被读取或被引用**，这是一项从零开始的数据采集。候选定义：

| 定义 | 采集点 | 问题 |
|---|---|---|
| 笔记详情页被打开 | 页面级 | 自己随手翻也算「出」，指标会虚高 |
| 从搜索结果点进笔记 | 搜索页 | 最接近「找得回」的语义 |
| 被 AI 引用（工具真返回过） | `search-notes.ts` | 最能体现知识库被「用」 |
| 写作侧栏相关笔记被点开 | `/related` | 体现主动发现的价值 |

**建议**：只采后三者，不采「随手翻」。因为这个指标存在的意义是回答「我的笔记真的被用到了吗」，把浏览算进去就失去了鉴别力。

需要新表 `note_usage_events(id, note_id, kind, created_at)`，`kind` 取 `search_hit` / `ai_cited` / `related_open`。历史数据无法追补，指标从上线日起才有意义——**这一点要在 UI 上说明**，否则第一周显示「出 0 条」会被误读为功能坏了。

风险：这是唯一会**新增写入路径**的任务（每次搜索点击都写一行）。需确认不拖慢搜索响应（异步写、失败忽略）。

### T4 · 「这条还成立吗」回顾

意图文档称此变体「未在任何竞品上观察到」，是差异化最强的一件，但技术上最简单——**可以几乎完整复用每周回顾的既有机制**：

- `src/lib/ai/weekly-review.ts` 的「每小时对表」模式（`settings` 记录进度 + `setInterval` tick），ADR 0012 已论证过为何不用日历定时器
- `aiJobs` 队列加一个 `type`，与 `weekly_review` 平级
- 沿用「产物即普通笔记」还是改为「卡片式提问」需要定：回顾的产物不是知识，而是一个**待用户回答的问题**，落成笔记可能反而污染知识库。倾向做成首页/收件箱里的轻量卡片，用户回答后可选择追加进原笔记

选取策略：优先挑「半年前创建、之后从未被修改、且不在回收站」的笔记，每周最多推 1–2 条。数量必须克制——这个功能一旦变成打扰就会被永久关掉。

风险最低，可作为 T1/T2 之间的填充任务。

## 7. 建议不做 / 降级的条目

**§5 的「降级项做成设置页默认关闭的开关」——建议不单独做。** 核对后发现该建议的目标已由其他设计基本满足：深度思考已是「消息级开关、默认关闭、刷新不记忆」；AI 画图需先在设置页配好图像模型才可用，未配置即不存在；手写摄取按需触发；Mermaid 是纯渲染能力，不占核心路径也不产生调用。再加一层开关只会让意图文档自己批评过的「配置墙」更高一层。

**§6 公网在线 demo——非代码任务，需你决定。** `docker-compose.demo.yml` 已就绪，缺一台机器和一个域名。意图文档判断这是「转化率最高的一次性投入」。我能做的是准备部署脚本与安全检查清单（demo 实例必须与正式实例完全隔离，且不得配置任何真实 API Key），机器与域名需要你提供。
