## 备份了什么

| 内容 | 形式 | 位置 |
| --- | --- | --- |
| SQLite 数据库（笔记、主题、标签、回收站、设置、对话、Token 记录及任务等） | 单文件快照 `app-YYYY-MM-DD.db` | 数据库同级的 `backups/` 目录 |
| 上传的图片（`uploads/` 全目录） | 明文目录 `uploads-YYYY-MM-DD/` | 同上 |

HEIC 图片的 JPEG 展示副本和 HEIC 原件都位于 `uploads/`，因此会一起进入图片快照。恢复时必须恢复整个目录，不能只复制笔记正文引用到的 JPEG。

- 应用启动 5 分钟后做第一次备份，之后每 24 小时一次；也可在 **设置 → 数据 → 立即备份** 手动触发（复用同一逻辑，覆盖当天快照）。
- 数据库快照与图片目录**分别**保留最近 **7 份**，更早的自动清理；这不是“保证保留 7 个自然日”。
- 快照文件名中的日期为 **UTC 日期**：北京时间早上 8 点前完成的备份会落在"昨天"的文件名里，属正常现象（以文件修改时间为准）。
- 每日备份**成功后**才调用清扫，处理到期回收站、孤儿图片和失效会话；手动备份不清扫。想找回已彻底删除的数据，需要在既有备份被覆盖或轮转前保存副本，不能承诺还能找回 7 天。
- Docker 部署时备份位于容器内 `/data/db/backups/`；使用 `docker-compose.yml` 默认绑定挂载时，宿主机路径为 `./data/db/backups/`。

数据库通过 SQLite backup API 先生成一致性快照，随后复制 `uploads/`。两步不是数据库与图片的原子联合快照；期间的上传、删除或 AI 写入可能造成差异。同日重复备份会覆盖数据库并重新复制图片，失败或中断可能留下不完整配对。**“同日期”是选取条件，不是完整性证明。**

若源 `uploads/` 不存在，现有实现仍可能只生成数据库并报告成功；设置页的最近备份时间也只依据数据库快照。恢复前必须核对配套图片目录、文件清单及实际图片，不能补一个空目录来掩盖缺失。确实没有上传过图片的库，也要先确认这一事实。

## 还需单独保存的内容

- **异地副本**：默认备份与工作库同盘。将核对过的配对快照另存到其他设备或加密异地存储，并复核文件哈希。
- **部署记录**：镜像 tag、image ID/digest、平台/架构、原 Compose project、实际卷名/绑定路径、Compose 与环境文件。`.env` 和部署配置不在数据库快照中。
- **Markdown 目录**：`data/notes` 是增量导出，不在自动备份的图片目录中；需要保留现有副本时单独保存，不与较早数据库快照混称为同一时点。

数据库会带回设置页保存的模型地址/API Key、API Token 记录、任务及功能开关。**空白 `LLM_*` 环境变量不会覆盖数据库配置**，见 [ADR-0001](adr/0001-llm-config-in-db.md)。恢复较早快照还可能带回后来才吊销的 Token；在恢复实例投入使用前重新核对凭据。备份、环境文件和明细清单只保存在自己的受控位置，不上传公开 Issue。

## 1. 核对源实例并取出配对快照

如果已有异地配对快照，可直接准备下面的 `snapshot/` 目录并核对清单。需要从原容器取出时，先记录实际容器名、project 和 `/data/db`、`/data/uploads`、`/data/notes` 挂载。Windows 可按[部署手册 §8.2](部署手册-tailscale.md#82-怎么升级新版本)读取；Linux 可用 `docker inspect --format '{{.Config.Image}} {{.Image}} {{json .Config.Labels}} {{json .Mounts}}' zhiliao`。示例容器名 `zhiliao` 须按实际替换，不按 `<目录名>_kb_db` 猜测源卷。

选取实际存在、已完成的备份。需要新备份时，先结束编辑和上传，在 **设置 → 数据 → 立即备份** 等待任务完成，再停止源容器后复制；不要在备份复制过程中停容器。出现中断、失败或缺图时保留现场，选择其他完整配对或使用已核对的冷备，不把当前 uploads 混入旧数据库快照。

### Windows PowerShell

以下以 `2026-09-12` 快照为例，日期和恢复目录须替换成实际值。恢复目录必须是新目录；`docker stop` 保留原容器和原卷，便于对照与回退。

```powershell
$ErrorActionPreference = 'Stop'
$sourceContainer = 'zhiliao'
$snapshotDate = '2026-09-12'
$restoreRoot = 'D:\kb-recovery\restore-20260913'
if (Test-Path -LiteralPath $restoreRoot) { throw '恢复目录已存在，请换一个新目录。' }
New-Item -ItemType Directory -Path (Join-Path $restoreRoot 'snapshot') | Out-Null

docker stop $sourceContainer
if ($LASTEXITCODE -ne 0) { throw '源容器未成功停止，停止复制。' }
docker cp "${sourceContainer}:/data/db/backups/app-$snapshotDate.db" (Join-Path $restoreRoot 'snapshot/app.db')
if ($LASTEXITCODE -ne 0) { throw '数据库快照复制失败。' }
docker cp "${sourceContainer}:/data/db/backups/uploads-$snapshotDate" (Join-Path $restoreRoot 'snapshot/uploads')
if ($LASTEXITCODE -ne 0) { throw '图片快照复制失败，不继续恢复。' }

Get-ChildItem -LiteralPath (Join-Path $restoreRoot 'snapshot') -File -Recurse -Force |
    Get-FileHash -Algorithm SHA256 |
    Export-Csv -LiteralPath (Join-Path $restoreRoot 'snapshot-sha256.csv') -NoTypeInformation -Encoding UTF8
Set-Location -LiteralPath $restoreRoot
```

### Linux / NAS

同样可以从停止的容器读取配对快照，不必直接改动正式绑定目录。下面在子 shell 中遇错退出，目录已存在时不会覆盖它：

```bash
(
set -eu
umask 077
source_container=zhiliao
snapshot_date=2026-09-12
restore_root="$HOME/zhiliao-restore-20260913"
mkdir "$restore_root"
mkdir "$restore_root/snapshot"
docker stop "$source_container"
docker cp "$source_container:/data/db/backups/app-$snapshot_date.db" "$restore_root/snapshot/app.db"
docker cp "$source_container:/data/db/backups/uploads-$snapshot_date" "$restore_root/snapshot/uploads"
cd "$restore_root"
find snapshot -type f -exec sha256sum {} + > snapshot-sha256.txt
)
```

全部成功后进入 `$HOME/zhiliao-restore-20260913`，后续文件和命令都在该目录内操作。

两种方式最终应得到：

```text
恢复目录/
  snapshot/
    app.db       ← 选中的 app-YYYY-MM-DD.db
    uploads/     ← 同次 uploads-YYYY-MM-DD/ 的完整内容
  snapshot-sha256.csv 或 snapshot-sha256.txt
```

原快照日期、取出时间与来源镜像记入部署记录，重命名为 `app.db` 只是为了统一下面的恢复输入。核对图片清单包含 JPEG 和存在的 HEIC 原件；只有数据库文件时停止。源实例若健康且本次仅为演练，可在复制核对后按原启动方式恢复服务；故障库则保持停止并保护现场。

## 2. 在独立目标恢复，先保持离线

下面只创建恢复副本，不挂载原卷、不覆盖正式 `data/`。数据库、图片和 Markdown 都使用本次 project 的新命名卷；**这与正式安装将 Markdown 绑定到宿主机 `data/notes` 的布局不同**，不要未经核对就替代原部署配置。

每次选择未使用过的 project 名；下文统一以 `zhiliao-restore-20260913` 为例。先用 `docker ps -a`、`docker volume ls` 核对没有同名 project 的旧资源；有则更换本节所有命令中的 project 名。准备阶段还会拒绝非空目标，重复执行失败后不要删除文件强行重试。

### 2.1 准备镜像和独立配置

使用**生成快照时对应的已发布镜像**，先验证恢复，再单独升级。例子仅针对 v0.6.0 快照；快照来自其他版本时，先确认其 tag/digest，不能将较新数据库直接交给 0.6.0。

```text
docker image inspect ghcr.io/b-tech-hub/zhiliao:0.6.0 --format '{{.Id}} {{json .RepoDigests}}'
```

镜像未缓存时先单独拉取相应固定镜像并记录身份。以下配置的 `pull_policy: never` 禁止恢复步骤隐式选择或拉取别的镜像。

在恢复目录新建 `restore.env`，设置独立密码和至少 32 字节的随机会话密钥；下列占位值必须替换，不复制正式 `.env`：

```dotenv
RESTORE_IMAGE=ghcr.io/b-tech-hub/zhiliao:0.6.0
RESTORE_APP_PASSWORD=替换为独立密码
RESTORE_SESSION_SECRET=替换为随机生成的64位十六进制字符串
TZ=Asia/Shanghai
```

已有原镜像 digest 时，`RESTORE_IMAGE` 可用已核对的 `ghcr.io/b-tech-hub/zhiliao@sha256:...`。不要设置 `DEMO_MODE`，不要套用 Demo 数据或 mock 配置。

新建 `compose.restore.yml`，内容如下。`prepare` 仅以 root 复制文件并将目标交给镜像内的 `node` 用户；`app` 沿用镜像的非 root 用户。两个服务都先使用 `network_mode: none`：

```yaml
services:
  prepare:
    image: ${RESTORE_IMAGE:?请设置 RESTORE_IMAGE}
    pull_policy: never
    network_mode: none
    user: "0:0"
    entrypoint: ["sh", "-euc"]
    command:
      - |
        test -s /restore/app.db
        test -d /restore/uploads
        test -z "$$(ls -A /data/db)"
        test -z "$$(ls -A /data/uploads)"
        test -z "$$(ls -A /data/notes)"
        cp /restore/app.db /data/db/app.db
        cp -a /restore/uploads/. /data/uploads/
        chown -R node:node /data/db /data/uploads /data/notes
    healthcheck:
      disable: true
    volumes:
      - type: bind
        source: ./snapshot
        target: /restore
        read_only: true
        bind:
          create_host_path: false
      - restore_db:/data/db
      - restore_uploads:/data/uploads
      - restore_notes:/data/notes
  app:
    image: ${RESTORE_IMAGE:?请设置 RESTORE_IMAGE}
    pull_policy: never
    network_mode: none
    restart: "no"
    environment:
      APP_PASSWORD: ${RESTORE_APP_PASSWORD:?请设置独立密码}
      SESSION_SECRET: ${RESTORE_SESSION_SECRET:?请设置独立会话密钥}
      DATABASE_PATH: /data/db/app.db
      UPLOAD_DIR: /data/uploads
      NOTES_EXPORT_DIR: /data/notes
      TZ: ${TZ:-UTC}
    volumes:
      - restore_db:/data/db
      - restore_uploads:/data/uploads
      - restore_notes:/data/notes
volumes:
  restore_db:
  restore_uploads:
  restore_notes:
```

数据库和图片原样写入**空目标**，因此没有旧 `app.db-wal` / `app.db-shm` 混入，也不会残留另一时点的图片。SQLite 快照不应搭配旧工作库的 WAL/SHM；如果拿到的是整目录冷备，则应保留它自己的完整 SQLite 文件集，不能套用本例只取 `app.db`。

### 2.2 核对配置、复制和启动

以下命令在 PowerShell 和 Bash 都可逐条执行。每条成功后再执行下一条；`prepare` 失败时保留源包与目标以便调查，重新尝试使用另一个空 project。

```text
docker compose --env-file restore.env -p zhiliao-restore-20260913 -f compose.restore.yml config --quiet
docker compose --env-file restore.env -p zhiliao-restore-20260913 -f compose.restore.yml config --images
docker compose --env-file restore.env -p zhiliao-restore-20260913 -f compose.restore.yml run --rm --no-deps prepare
```

`config --images` 中两个服务都应使用已核对的同一镜像。复制成功后，先用同一镜像内的 SQLite 模块只读检查恢复副本；此命令覆盖应用启动入口，不启动 worker：

```text
docker compose --env-file restore.env -p zhiliao-restore-20260913 -f compose.restore.yml run --rm --no-deps --entrypoint node app -e "const db = require('better-sqlite3')('/data/db/app.db', {readonly:true,fileMustExist:true}); const rows = db.pragma('integrity_check'); console.log(JSON.stringify(rows)); db.close(); if (rows.length !== 1 || rows[0].integrity_check !== 'ok') process.exit(1)"
```

预期为 `[{"integrity_check":"ok"}]` 且退出码 0。模块缺失、数据库打不开或检查不通过时都停止，不跳过检查。通过后再启动离线应用：

```text
docker compose --env-file restore.env -p zhiliao-restore-20260913 -f compose.restore.yml up -d app
```

启动会迁移目标数据库、检查全文索引，并启动任务与备份调度；离线状态只阻止网络通信，不冻结目标数据库的任务状态。源快照只读挂载在 `prepare`，源卷从未挂入恢复实例。

确认应用已经启动后，检查非 root 用户对三个目录的写权限，以及容器内部健康端点：

```text
docker compose --env-file restore.env -p zhiliao-restore-20260913 -f compose.restore.yml exec -T app node -e "for (const p of ['/data/db','/data/uploads','/data/notes']) require('node:fs').accessSync(p, 2)"
docker compose --env-file restore.env -p zhiliao-restore-20260913 -f compose.restore.yml exec -T app node -e "fetch('http://127.0.0.1:3000/api/healthz').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"
```

两条命令都应返回退出码 0。健康接口只做数据库基本探测，**不能证明全库与图片完整**。失败时读取当前 project 的 `logs --tail 50 app`，保留必要的脱敏片段；不清理原库的 WAL/SHM，也不改原卷权限。

## 3. 界面、图片与数据出口核验

离线实例没有发布端口。要在浏览器核验，先确认恢复库的模型供应商、允许发送的数据范围与预算；恢复的后台任务和每周回顾可能在联网后立即调用原模型。**仅换端口或使用独立 project 不会阻止这些调用。** 不允许联网时继续保持离线，将界面与真实模型检查记为未执行，不通过清空环境变量假设已禁用模型。

允许该恢复副本联网后，在同一目录新建 `compose.restore-ui.yml`：

```yaml
services:
  app:
    network_mode: bridge
    ports:
      - "127.0.0.1:3302:3000"
```

确认 3302 未被占用，然后只叠加这一份界面配置启动；不叠加正式 Compose 或 Demo 文件：

```text
docker compose --env-file restore.env -p zhiliao-restore-20260913 -f compose.restore.yml -f compose.restore-ui.yml up -d app
```

访问 `http://127.0.0.1:3302`，用独立恢复密码登录。这是本机入口，未提供公网或 Tailscale 发布。按下表逐项记录预期、实际与证据：

| 检查 | 通过依据 |
|---|---|
| 数据库与笔记 | 先通过 SQLite integrity_check，再对照选定快照的计数、主题、标签、时间和代表性长短笔记；正文可完整打开。健康检查不替代这两步 |
| 图片 | 多条含图笔记可打开，图片清单与源快照一致；存在 HEIC 时同时核对原件和 JPEG，不只看缩略图 |
| 搜索与会话 | 关键词可找回已知笔记，既有会话与来源可读取；真实模型回答和拒答只在已允许发送的样本范围验证 |
| 写入与持久化 | 在恢复副本写一条专用验收笔记，重新打开、重启 app 后仍在；记录实际目标 project 和卷 |
| 增量 Markdown | 新增或修改笔记会写到恢复实例 `/data/notes`；单独复制该目录核对实际文件，不据页面保存成功推断导出成功 |
| ZIP 数据出口 | 设置 → 数据 → 导出全部数据，检查 Markdown、展示图片与 `assets/originals/`；往返导入与判重在另一个空实例验收 |
| 源数据保护 | 重新核对保留源包的 SHA-256 未变，原 project 与数据卷未被替换；记录本次恢复耗时、失败点和回退结果 |

**恢复数据库不会自动全量回填 Markdown 目录。** 当前导出由笔记写入、AI 处理或回收站恢复等事件触发；已有笔记需要完整可读副本时先使用 ZIP 导出，不能将空的 `restore_notes` 视为全库已导出。原宿主机 `data/notes` 可另存作参考，但较晚的文件不能混入较早快照并宣称同一时点，见 [ADR-0020](adr/0020-incremental-markdown-export.md)。

## 4. 停止、回退和正式接管

核验结束或任一关键项失败，先停止恢复实例，保留卷、源包、配置和证据：

```text
docker compose --env-file restore.env -p zhiliao-restore-20260913 -f compose.restore.yml stop app
```

- **原实例健康，只做演练**：原卷与配置未改变，可按原目录、原 project 和原环境文件重新启动原实例。恢复副本中的验收笔记不回写到原库。
- **恢复副本失败**：保护源快照与故障现场，修正原因后另建空目标重试；不要将部分恢复结果覆盖到正式卷。
- **升级失败**：使用升级前镜像和升级前配对快照在新目标恢复；已迁移数据库不能仅降级镜像。不将旧 WAL/SHM 搭配到 SQLite backup API 生成的快照。
- **准备正式接管**：先停止旧实例，确认验收结果，再制定明确的入口切换、持久化和重启配置。核对真实卷名、Markdown 宿主目录、密码/Token、模型设置和备份落点；本节的离线/界面演练配置不自动替代正式配置。演练已改变目标数据时，用保留源包重新建立干净目标。切换失败先停新实例，只有原数据仍适用时才接回原实例；切换后的新增笔记须另存，不能承诺自动合并。

暂时保留恢复资源便于复核。确认放弃演练数据后，才按记录核对并回收本次 project 的容器和三个卷；`down -v` 会删卷，不能对原 project 使用，也不能按含糊前缀批量删除。原快照及异地副本不随演练清理。

## 本地开发与整目录冷备

本地开发通常使用 `./data/`，但仍先核对 `DATABASE_PATH`、`UPLOAD_DIR`、`NOTES_EXPORT_DIR` 的实际值。停止 dev 服务、worker 和所有其他写入进程后，整目录复制到新的备份位置，保留当时的 `app.db`、`app.db-wal`、`app.db-shm`（若存在）、完整 uploads、notes 与配置记录。**运行中直接复制 `app.db` 不是一致性冷备。**

冷备中的 SQLite 文件集需要作为同一时点处理。实际恢复同样先复制到独立位置，用匹配版本验证；不要在原开发目录删除 WAL/SHM 后覆盖文件。若改用自动/手动备份生成的单文件快照，则按上面的空目标方法恢复，不带入工作库的 WAL/SHM。

## 导出与备份的区别

| 方式 | 用途与边界 |
|---|---|
| 增量 Markdown | 方便日常阅读；按写入事件更新，不能单独还原数据库设置、会话和任务，也不能证明图片完整 |
| 导出全部数据 ZIP | 有效笔记的迁移与阅读；包含 Markdown、引用的展示图片和 HEIC 原件，不含回收站及完整内部状态 |
| 立即备份 / 每日备份 | 数据库快照加完整 uploads 配对，用于恢复内部状态；需核对一致性并另存异地副本 |
| 停机整目录冷备 | 所有写入停止后保留完整文件集与部署记录；恢复时保持同一时点，不与其他版本或日期的文件混用 |

手动备份入口为 **设置 → 数据 → 立即备份**；进行中的重复请求会合并，同日完成的下一次备份会覆盖当天快照。复制出需要长期保留的版本后再继续日常轮转。ZIP 的往返能力见 [ADR-0024](adr/0024-markdown-zip-import.md)，它不能替代完整数据库恢复。
