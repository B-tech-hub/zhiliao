### Nginx 300 秒场景与判定

正式取证使用专用 `nginx/demo-proxy.conf` 的固定 Nginx digest，保持真实的 300 秒设置。专用上游使用服务名 `proxy-upstream:3000`，由候选镜像内的 Node 运行夹具提供；这只验收代理行为，应用 SSE 继续引用已有证据。

| 场景 | 输入 | 期望与取证 |
|---|---|---|
| 响应头前静默 | 上游接受请求后不发送响应 | 约 300 秒后出现 504，并有对应请求的上游读取超时日志 |
| SSE 中途静默 | 先发送响应头和首个正文事件，随后停止发送 | 从最后一次上游数据起约 300 秒后连接异常结束；已有 HTTP 200 不能作为成功，必须没有正常 `done`，并匹配读取超时日志 |
| 长连接心跳 | 每 60 秒发送一次事件，持续 360 秒后正常结束 | 总时长超过 300 秒仍可正常完成，证明读超时约束相邻读取间隔，而不是整次请求总时间 |
| 上游停止读取请求体 | 上游在已识别请求后暂停读取；客户端使用固定大小缓冲区流式发送，最多发送 32 MiB | 必须实际阻塞 Nginx 向上游发送，并匹配请求发送超时日志；区分 30 秒 `client_body_timeout`、读取超时与客户端自身预算耗尽 |

读超时初始容差建议为 295–330 秒；发送超时还需记录实际停止进展的时刻与 Nginx 日志原因。客户端单场景总预算为 450 秒，应用层不提前用已有 SSE 探针的 5/30 秒预算取消。实际时限、观测值和日志归因都写入结果，不能只返回布尔值。

若发送场景被另一条时限先终止，或 32 MiB 数据仍未形成发送阻塞，应记录未覆盖原因；不自动增大负载或改写 Nginx 超时值。缩短时限的夹具只用于调试和局部回归，不计入 300 秒验收证据。

四个请求可在同一验收进程中并发发起，不启用多 Agent。预计整个本机真实验收约 8–12 分钟，期间至少每 30 秒报告进度；准备和运行批准时再次列明实际场景与预算。

### 已批准执行的计时维护与复验

执行前事实：[只读环境记录](验收证据/story-2-2-clock-environment-2026-09-12-a2.json)显示 WSL 2.5.10.0、内核 6.6.87.2-1，原时钟源为 `tsc`，可选 `hyperv_clocksource_tsc_page`、`hyperv_clocksource_msr` 和 `acpi_pm`。Ubuntu-24.04 与 docker-desktop 均在运行。用户选择第 1 项并要求继续后，已执行下列临时对照；结果证明本次 Hyper-V 候选没有消除计时偏差。

获准流程为一次临时对照，执行前已重新核对当前值仍为 `tsc`、候选源仍可用：

1. 临时切换到 Hyper-V 提供的 `hyperv_clocksource_tsc_page`，确认读取值与目标一致。
2. 使用无业务卷的本次候选探针，至少比较两段 20 秒的宿主机/虚拟机单调计时，同时记录调用往返误差。只有计时差可确认不超过 1% 时才继续长时复验；否则停止并恢复。

6. 无论正常、失败还是连接中断，均由清理流程和看门狗确保在暂停上限内恢复。先停止本次探针、恢复本轮保存的 tick 并读回，再在核对同一 exe/启动时间后发送 `SIGCONT`，确认原进程恢复运行；只恢复本轮实际暂停的任务。核对并清理本次资源，复查既有实例及文件保留情况，恢复失败立即报告。

| 动作 | 作用对象 | 结束处理 |
|---|---|---|
| 管理员只读预检 | WSL 根 PID 命名空间中的目标进程、活动参数及参考时钟 | 记录身份依据；无法核实即退出 |

| `ADJ_TICK=10000` | 共用 WSL 内核 | 恢复本轮实际起始值并读回 |
| 四场景代理复验 | 本次隔离代理 project | 按运行标识清理容器、网络和临时配置 |

影响与风险：暂停的是共用 WSL 内核的时间校正任务，会影响 Ubuntu、Docker 及其他 WSL 程序的时钟校正和超时速度。恢复 chronyd 后，它可能重新采用原参考和补偿值；受控复验通过只能证明该维护条件下的代理行为，不代表日常环境已永久修复。PID 复用、管理员通道失效和恢复失败是必须提前处理的风险，不能把“准备了恢复命令”当作恢复已经成功。

当前理解：首轮辅助脚本退出了根调试 shell；WSL 2.5.10 的启动及退出处理与后续无输出的实测一致。已核对现有 CLI 支持 `docker desktop stop/start --timeout`。当前 Ubuntu-24.04 与 docker-desktop 正在运行，Ubuntu 存在两个交互 bash 会话；7 个既有 Docker 容器均为 exited，其中 6 个重启策略为 `no`，知了正式容器为 `unless-stopped`。

1. 执行前重新记录两个发行版、WSL/Engine 版本、7 个容器的状态/重启策略、镜像、挂载、网络与保留文件哈希。仅在既有容器仍全部停止、策略仍为上述值时继续；发现运行中的既有容器、额外发行版或状态变化时先停下核对，不扩大关闭范围。

3. 用 `docker desktop start --timeout 120` 恢复原本运行的 Docker Desktop，再用 `wsl.exe -d Ubuntu-24.04 -u root -- true` 恢复原 Ubuntu 发行版。确认 Engine 响应、两个发行版运行、7 个容器仍停止且持久化挂载不变；不自动启动正式容器。恢复失败立即留证报告，不循环重启或升级。
4. 重启后的 PID、命名空间与启动时间全部重新获取。管理员根通道先等待提示符，操作完成后保留 shell，仅关闭本次 Windows 转发进程；在通道往返和异常退出机制核对成功前，不暂停任何任务。确认当前 chronyd 可执行文件、父进程、启动标识和活动配置，不再要求复用重启前的 PID 308。
5. 先用只读查询和两段 20 秒对照检查重启后的原始/普通单调时钟。若均满足 1% 门槛，直接执行原四个代理场景；否则按上节已经批准的范围准备独立恢复看门狗，核对本轮同一进程后暂停最多 600 秒、临时 `ADJ_TICK=10000`、两段达标后再复验，结束恢复本轮实际起始 tick 和进程运行状态。一次重启周期内最多进入一次四场景复验，失败不循环校正。
6. 保持 300 秒配置、295–330 秒容差、450 秒探针预算与 32 MiB 上限。按运行标识清理本次资源，另存 JSON，比较既有容器与文件；对重启造成的环境变化如实记录。原网络 20 项只保留为其原运行环境的历史证据，不能据此推断重启后或目标主机的全部路径通过。

影响范围为本机整个 WSL2 虚拟机与 Docker Desktop 引擎，包含当前两个发行版的进程；不只是代理验收容器。容器卷及仓库文件保留，容器停止状态须读回确认。重启后时钟是否正常仍未知，一次受控通过也不等于长期计时问题已经修复。

## B1：Windows Desktop 业务卷能力与硬配额缺口

### 当前结论与本轮处理

本机普通 local named volume 没有已配置、可验证的逐卷容量硬上限，原 B1 尚不具备实施和关闭条件。保留现有三个业务卷及其持久化语义，完成上述能力记录；本轮不新增 `scripts/manage-demo-volume-quotas.sh`，也不执行灌满卷的试验。

Docker 的 local 卷驱动把选项交给 Linux 挂载机制，本身不额外提供通用的持久卷 `size` 限额。`tmpfs size` 会失去业务数据持久性，容器可写层 `storage-opt size` 不限制挂载卷，Desktop 整体数据盘容量也不是三个卷各自的配额。官方提供的 loop 块设备示例明确不是通用推荐做法；本轮不据此承诺已具备稳定的 Desktop 存储方案。

用户选择“仅本机”允许当前阶段按本机验收范围推进，但不撤销原容量验收要求。汇总中分别记录“本机所选检查通过”和“业务卷硬配额未满足”；后者不得写成 `passed`、`done` 或被本机模式自动忽略。

### 初始容量

| 卷 | 建议硬上限 | 容量用途 |
|---|---:|---|
| `demo_db` | 512 MiB | SQLite 数据库以及 WAL/SHM 等同目录文件，共用这一上限 |
| `demo_uploads` | 1 GiB | 图片总量；现有单图片 20 MiB 限制继续生效 |
| `demo_notes` | 256 MiB | Markdown 导出和必要的临时导出文件 |
| 合计 | 1.75 GiB | 仅三个业务卷，不含镜像、容器日志与已有受限 tmpfs |

这是公开、可重置 Demo 的首版建议值，不是当前已生效配置或性能测量结论。它为数据库写入和演示附件留出余量，并使一次完整容量触发验收的写入预算有界。后续调大上限仍需复核目标主机容量与实测结果。

### 条件性参考：以后需要硬配额时

在原生 Linux Docker Engine 主机上，对三个普通 local named volume 的真实数据目录分别设置 XFS project quota。前提是这些卷实际所在文件系统为 XFS，已开启项目配额记账和强制执行；检查对象必须是 Docker 服务端的卷路径，不能只检查运行 CLI 的工作站。

保留三个 named volume 名称与容器内路径，不把业务卷换成 tmpfs、Windows bind mount，也不通过容器可写层的 `storage-opt size` 声称限制了挂载卷。主 Compose 的跨平台布局继续保留。

该参考需要另行选择具备条件的存储环境，与本轮已选择的 Desktop 普通卷不相符。若以后仍要求在本机实现持久硬配额，应先评估受支持存储层或独立 Engine，再确认实际方案；本轮不预设另一套 Engine、特权存储助手或磁盘镜像方案已获批准。

### 配额工具与生命周期

以下是未来容量方案必须保留的验收要求，不是本轮将执行的步骤。只有目标存储前提及具体方案另行确认后，才考虑实现 `scripts/manage-demo-volume-quotas.sh` 或对应平台工具。

### 影响范围与风险

本次改动集中于两个验收入口、对应测试和文档。真实执行临时创建三个 Demo 容器、两个网络、三个空业务卷，以及网络工具自己的控制资源和本机临时监听；沿用现有 CPU、内存、PID、日志与只读限制。结束时已删除本轮验收数据，既有 7 个停止容器和 8 个卷仅作只读保留核对。

主要风险是误把网络阶段失败记成通过、清理时混淆两组运行标识，以及无硬配额却扩大验证数据量。通过异步等待、双层归属检查、失败非零和固定探针范围控制这些风险。资料不完整或清理失败时保持待验收，不能靠重跑覆盖失败。一次正常计时记录也不代表 WSL 长期计时问题已解决。

### 验收标准

- Given 未选择网络选项，When 使用原 PowerShell/Node 入口，Then 原 HTTP/SSE 行为及显式保留资源语义不变，不创建网络对照资源。

- Given 网络失败、异常、报告缺失或清理失败，When 汇总退出，Then 返回非零并保留失败依据，仍尝试清理归属可核实的本轮 Demo，不删除外来资源。
- Given 本机入口实际绑定回环地址，When 检查发布端口与应用挂载，Then 仅 ingress 发布指定端口，app/mockllm 无宿主机端口，Demo 不挂载正式目录、卷或环境文件。
- Given 本轮所选检查全部通过，When 完成收尾，Then 本轮容器、网络、卷和临时凭据无残留，既有实例及保留文件核对通过；只关闭本轮覆盖的本机路径。
- Given 尚无业务卷硬配额、实际正式服务正向对照、公网 HTTPS 和新发布镜像证据，When 更新状态，Then 明确保留这些未完成项，Story/Sprint 继续 `in-review` / `review`，不进入 Story 2.3。

## 依据

- [Docker Volumes](https://docs.docker.com/engine/storage/volumes/)：local 驱动将挂载选项传给 Linux 挂载机制，本身不提供额外的通用容量限制。

- [Linux XFS 管理文档](https://github.com/torvalds/linux/blob/master/Documentation/admin-guide/xfs.rst)：区分项目配额记账与强制执行，以及 `pquota`/`prjquota`/`pqnoenforce`；本轮核对的 Git blob 为 `acdd4b65964c058647a7b383d8c2c778777a538e`。具体 `xfs_quota` 命令及生命周期操作须在实现时对照目标版本手册。
