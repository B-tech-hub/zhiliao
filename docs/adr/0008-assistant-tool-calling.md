# 0008. AI 助手采用工具调用，写操作以操作卡片与撤销兜底

日期：2026-08-15

状态：已采纳（部分取代 [0003](0003-chat-context-injection.md)）

## 背景

ADR-0003 把 AI 对话定为「围绕当前笔记或主题」：上下文直接注入 prompt，不做检索。这个形态下 AI 只能**读**，而且只能读用户此刻打开的那一份。三类真实需求因此全部落空——「看看这个网址讲了什么」「帮我记一条」「把未分类里跟跑步有关的都归到跑步主题」。

它们看似三个独立缺失，实为同一个缺失：`src/lib/llm.ts` 的请求体只有 `{model, messages, temperature, stream}`，**没有 `tools` 参数**，整条链路没有「工具调用回合」的概念。补一个功能补不出来，得先补这个概念。

## 决策

### 一、以工具调用取代继续扩大上下文注入

新增 8 个工具（`src/lib/ai/tools/`）：`search_notes` `read_note` `list_topics` `create_note` `append_to_note` `update_meta` `delete_note` `fetch_url`。**写工具一律复用既有 lib 函数**（`note-write.ts` / `notes.ts` / `trash.ts`），不新写绕过 FTS 同步、锁字段与回收站语义的第二条写入路径——v0.2 在「17 处过滤点」上已经付过一次学费。

作用域随之统一为**全局**：当前笔记/主题降级为面板顶部可摘除的**上下文附件**。ADR-0003 的作用域前提就此被推翻；但那份 ADR 的另一半——**不建向量索引、不做全库 RAG**——仍然成立，`search_notes` 走的是 v0.1 就有的 FTS 关键词检索。

不继续扩注入的理由有两层：

- 注入的本质是「先替用户猜他要看什么，再一次性塞进去」。猜错白烧 token，猜不全答不出，而全库注入在任何上下文预算面前都不成立。工具调用把「取什么」的决定权交给模型，按需、多次、可迭代。
- 更根本的是**注入只能读**。「建一条笔记」「改主题归属」无论上下文开到多大都做不到——那是另一个方向的能力，只能由工具提供。

### 二、写权限全开，唯独禁止正文覆盖

建 / 追加 / 改元数据 / 删（进回收站）全部开放，**但没有覆盖正文的工具，且这是刻意的**。

ADR-0007 已明确不做版本历史。因此正文一旦被覆盖，旧内容**不存在任何找回渠道**：回收站救的是整条笔记而非某一版正文，每日备份最好也只能回到昨天，且要牺牲当天其余全部改动。相比之下另外四种写操作各有无损或近无损的反向路径（见下），正文覆盖是**唯一不可恢复的操作**——把它交给一个可能被网页内容策反的模型，风险与收益完全不对等。

模型若反复尝试改写正文，那是 system prompt 该引导的事（`chat-context.ts` 的提示词已写明「你没有覆盖或删改已有正文的能力」，并要求引导用户手动编辑），不是加一个工具来解决的事。

### 三、只有 `delete_note` 需要确认，其余直接执行

其余写操作直接执行，在对话里留下**操作卡片**，可逐条撤销。

判据不是「危险程度」而是**用户是否有机会后悔**。撤销依赖用户看见那张卡片——而删除是唯一一个「用户没看见就再也想不起来」的操作：笔记从列表、搜索、计数里一起消失，他不会知道少了什么，也就不会去点撤销。建/追加/改元数据都留在原地，看到不对再撤即可。

所以删除走**确认卡片**：先发 `{confirm_required}` 结束本轮 SSE，用户点「允许 / 拒绝」后由 `POST /api/chat/confirm` 接手续跑。确认卡片上写的是笔记**标题**而非 id——要用户拍板删不删却只给他一串 id，等于让他盲点。

## 配套改造（实现约束）

以下六条都是实现期间被实测推翻或补出来的，与直觉相左，且原计划里没有：

1. **撤销的乐观锁判据是状态指纹，不是 `notes.updatedAt`。** 原计划用 `updatedAt` 比对，实测在本项目根本不可用：`process-note.ts` 在 AI 处理完成时会写 `updatedAt: Date.now()`，而 `create_note` / `append_to_note` 都会重新入队 AI——助手刚建的笔记几秒后 `updatedAt` 必被刷新，用户点撤销时必然被判「已被修改」，**新建的笔记将永远撤销不了**。改为按工具计算指纹（`tools/types.ts` 的 `fingerprint()`），只覆盖该工具真正改动的字段：建/追加比对正文，改元数据比对主题+标题+标签，删除不设指纹（反向操作是从回收站恢复，不覆盖任何内容）。元数据指纹按写入后**读回**的实际值计算，因为标签经 `replaceNoteTags` 会去重规范化，用入参算会与读回值对不上。
2. **单轮工具调用数上限 20**（`chat-loop.ts` 的 `MAX_CALLS_PER_ROUND`）。轮次上限 8 管不住「一轮里发几十个写操作」这一维：被网页内容策反的模型可以一口气建 50 条笔记，虽然每条都有卡片可撤销，但用户得点 50 次。取 20 而非更小，是为了不误伤正常的批量归类。
3. **工具结果总预算 8000 字符，但最新一条无条件保留**（`applyToolBudget`）。从最新往回累加，超出的替换为省略提示。最新一条豁免的理由：它可能单条就接近 8000（`runTool` 的单条截断上限），若一并省略，模型拿不到刚刚执行的结果，会陷入反复重试。
4. **待确认的调用也要落成 `role:"tool"` 消息**（内容为「等待用户确认」）。否则那条 assistant 的 `tool_calls` 永远找不到配对结果，下次回灌历史时被供应商以 400 拒绝。同批次里排在待确认之后的调用同样不执行、但仍回灌一条「未执行」的结果，理由相同——**配对不能断**。历史按条数截断（`MAX_HISTORY = 20`）时极易只截到 tool 结果而丢掉发出它的 assistant，`buildLlmMessages` 因此把落单的一律丢弃；这类 400 的报错信息指向 `tool_call_id` 而非截断本身，不预先设防极难定位。
5. **撤销走 `restoreNote` 而非 `updateNote`**（`src/lib/note-write.ts`）。`updateNote` 会强制置锁并对正文变更重新入队 AI，而撤销是「回到原状」而非一次新编辑——沿用它的话，撤销一次 `update_meta` 就会把锁位一并置上，该笔记从此永久失去 AI 自动整理。`restoreNote` 按快照回写，锁位由快照原样恢复，正文变更不重新入队。不在撤销模块里直写 `notes` 表，是为了不让刚收敛的单一写入路径再次裂开。附带一个外键陷阱：快照里的主题可能已被用户删除，直接写回会抛 `FOREIGN KEY constraint failed`（`notes.topicId` 有外键且 `foreign_keys=ON`），撤销按钮变成一个 500——指纹校验拦不住它，因为删主题不改这条笔记的 `topicId`，指纹不变。现在跳过主题这一项，其余字段照常恢复。
6. **会话列表不再按 scope 过滤**，改为按最近更新倒序列出全部（上限 100 条），旧会话标注「围绕 XX」。助手已是全局的，若还按上下文附件把历史切成互不可见的若干份，用户在首页会一条历史都看不到。

## 备选方案与否决理由

1. **继续扩大上下文注入 / 改做全库 RAG**：见「决策一」，注入解决不了写操作；RAG 的复杂度在 ADR-0003 已否决过一次，且 `search_notes` 让模型自己迭代查询，实际召回不比一次性向量检索差。
2. **所有写操作都要确认**：把「AI 助手」退化成「AI 建议 + 手工执行」。批量归类十几条要点十几次确认，用户会直接不用这个功能。改用「直接执行 + 逐条撤销」，代价只在于用户需要看一眼卡片。
3. **一个都不确认，全靠撤销**：删除的撤销依赖用户看见卡片，而删除恰好是唯一「看不见就想不起来」的操作。见「决策三」。
4. **加 `overwrite_note` 工具，配套补版本历史**：版本历史在 ADR-0007 已按「痛点是整条找回而非改坏回滚」否决，为一个工具反悔整条决策不成比例。
5. **`updatedAt` 乐观锁**：见「配套改造 1」，与本项目的后台 AI 流水线直接冲突。回归用例固定在 `tests/lib/undo.test.ts`「后台 AI 处理刷新 updatedAt 后依然可以撤销」——写完做变异检验，把判据退回 `updatedAt` 该用例立刻变红，确认这个 bug 是真实的而非臆测。

## 后果

- 新增迁移 `0006_assistant_tools`（声明在 `src/db/migrations.ts`）：`messages` 新增 `toolPayload`（nullable JSON，存工具调用与撤销快照，重开会话据此重建操作卡片），`role` 允许 `"tool"`，`conversations.scopeType` 允许 `"global"`。**语义变更但零数据迁移**：scope 从「归属维度」降为「会话创建时的上下文快照」，历史会话原样可用。
- **全局会话必须在孤儿清扫里单独豁免**，这是上述 scope 语义变更的直接代价。`src/lib/trash.ts` 的存活判定原本按 scope 反查对象，而全局会话的 `scopeId` 是空串，落到 note/topic 任一分支都查不到 → 被判孤儿 → 每日清扫会把用户**全部**助手会话连同撤销载荷删光。这个缺陷从批次 C 起就埋着，直到全局助手成为主入口才显形，属数据丢失级。
- 新增两个端点 `POST /api/chat/undo`、`POST /api/chat/confirm`；`/api/chat` 重构为工具循环，SSE 事件在 `{delta}` `{done}` `{error}` 之外新增 `{tool_start}` `{tool_end}` `{confirm_required}`。循环逻辑落在 `src/lib/ai/chat-loop.ts` 而非 route handler：六条分支（无调用 / 有调用 / 待确认 / 被跳过 / 超轮次 / 预算超限）塞在 route 里只能靠起服务做端到端测，抽出来可以直接喂字符串断言。
- 模型不支持工具调用时降级为纯问答（探测结果存 `settings` 表的 `llm_supports_tools`）。静默忽略 `tools` 参数的供应商走的是「本轮没有工具调用」这条正常路径，不会卡住，只是能力退化，面板顶部有提示。
- **提示注入的实测尚未做过**：mock LLM 不会被说服，真实模型的表现未知。写工具不需确认，因此一次成功的注入可以污染笔记——防线是操作卡片（用户看得见）与逐条撤销（改得回来），而非阻止模型上当。接入真实供应商后应补一次实测。
- 验收项见 `tests/lib/chat-loop.test.ts`（配对校验、单轮上限、待确认后中断、预算裁剪）、`tests/lib/undo.test.ts`（四种反向操作与指纹判据）、`tests/lib/ai-tools.test.ts`、`tests/lib/chat-state.test.ts`（卡片状态机与引用白名单）。
