# 0010. 来源问答：严格接地的会话类型

日期：2026-08-15
状态：已采纳

## 背景

助手（[0008](0008-assistant-tool-calling.md)）能检索全库、也能自由使用模型自身的知识。这在「帮我记一条」「找找我写过什么」这类场景下很好用，但它无法回答一个用户经常真正想问的问题：**「就我记过的这些东西，能得出什么结论？」**

区别不在于能不能查到笔记，而在于**答案的边界是否可信**。当前形态下，一段回答里哪些出自用户的笔记、哪些是模型的常识补充，用户无从分辨。NotebookLM 的核心价值恰恰是划出这条边界：先选定来源，然后所有回答都只出自来源。

## 决策

新增会话类型「来源问答」（`conversations.scope_type = 'sources'`），三条核心约束：

**一、来源集挂在会话上，主题是活引用。**
新增 `conversation_sources` 关联表，存笔记 id 与主题 id 的引用。不引入独立的「笔记本」实体——单用户、极简是产品前提，为可复用的来源集铺一整套命名/列表/删除 UI 与它带来的价值不相称。主题作为来源时只存主题 id、提问时现查其下笔记，因此后续新增到该主题的笔记会自动进入来源范围（**活引用**而非快照）。笔记库是活数据，快照语义会制造「我明明加了笔记，AI 为什么看不见」的困惑。

**二、取内容用「注入优先 + 限域工具」的混合机制。**
来源全文在预算内（12000 字符）直接注入 system；超预算改注入来源清单（标题 + 摘要），正文交给限定在来源集内的 `search_notes` / `read_note` 按需取。不建向量索引——[0003](0003-chat-context-injection.md) 的这条结论在此明确保持不变。

**三、严格接地是会话级不变量，用户要求也不破例。**
来源里没有的，一律回答「来源笔记中没有相关内容」。用户在对话中说「那你用自己的知识说说」时，模型应引导他新建一场普通对话，而不是当场破例。

配套的工具边界：禁用 `fetch_url`（抓来的网页不是来源），保留四个写工具与 `list_topics`（写操作不影响回答的接地性，「把结论存成笔记」是高频需求），`search_notes` / `read_note` 限定在来源集内且在执行层二次校验。

## 备选方案与否决理由

1. **只加「严格接地」开关，来源沿用现有 scope（当前笔记/主题/全库）**：改动最小，但 scope 跟着页面自动切换，用户永远搞不清此刻的边界到底是什么。边界不清等于没有边界。
2. **只做多选来源，不改接地强度**：不解决核心问题——用户依然分不清哪句话出自自己的笔记。
3. **来源集做成独立可复用实体**：产品上更完整，但多一张表、一套 CRUD UI 与生命周期问题（来源集删了，底下的会话怎么办）。会话已有持久化与列表 UI，挂上去是白赚的。「沿用上次来源集」按钮能覆盖大部分复用需求。
4. **主题来源存快照**：行为可预测，但与「笔记库是活的」这一事实冲突，且用户加了笔记却不生效时没有任何提示。
5. **未命中时可显式豁免 + 标注「以下不来自你的笔记」**：体验更顺，但把不变量降级成逐条承诺，模型在多轮后极易滑向混答，且这类标注一旦被遗漏，用户是察觉不到的。真正的价值在于**不必逐句怀疑**，softening 会把它整个抵消。
6. **段落级引用**：需要稳定的块 id，而正文以 Markdown 原文落库、块编辑器在远期规划里；笔记本身通常不长，笔记级定位已够用。

## 后果

- **`scope_type` 新增取值必须过一遍全部读点。** [0008](0008-assistant-tool-calling.md) 时期新增 `'global'` 曾漏掉 `trash.ts` 的孤儿判定分支，每日清扫会删光全部会话（数据丢失级）。本次连同修法一起改掉：孤儿判定改为显式列举，**未知 scope_type 默认存活**——宁可留孤儿，也不能因为漏一个分支就删数据。
- **来源被删光不等于会话失效。** 硬删笔记会清掉指向它的来源引用行，一场会话可能变成零来源，但历史消息与撤销载荷必须留着。孤儿判定绝不能写成「来源数为 0 即孤儿」。
- **续聊必须用会话自己存的 scope。** 原先 `/api/chat` 用请求参数里的 scope（跟着当前页面走），一旦有来源问答，从历史里打开再发言就会静默丢掉整个来源集。已改为会话存在时以会话自身的 scope 为准。
- **引用白名单要包含来源笔记。** 全文注入的来源没经过任何工具，不放行会把来源问答里的引用全部降级成纯文本。服务端在开流前先发一个 `grounding` 事件回报展开后的笔记 id。
- **提示注入的攻击面变了。** 来源正文进入的是 system 位（特权位置）而非工具结果位。[0008](0008-assistant-tool-calling.md) 记录的提示注入实测是在工具结果位做的，其结论不自动适用于本模式，已按同样方法重测一轮（2026-08-15，真实模型 glm-5.2，注入写进来源笔记本身，露骨版与伪装成产品自检流程的隐蔽版**都未得手**，核库无新建/删除、无密码泄漏，详见[开发日志](../开发日志.md)）。仍是单一模型的一轮抽样，换模型或改写提示词后应重测。兜底仍是操作卡片与逐条撤销，而非指望模型不上当。此外来源集限域本身也是一道防线：不在来源集里的笔记，模型即便上当也取不到。
- **超预算是静默降级的风险点。** 来源集过大时正文不在上下文里，若模型又不支持工具调用，「严格接地」会变成「严格接地到清单」。UI 必须显式提示，否则用户会把「没找到」误解为「我的笔记里确实没有」。
- 长度预算仍按字符数近似，全项目没有 tokenizer——这是既有限制，本次未改变。
