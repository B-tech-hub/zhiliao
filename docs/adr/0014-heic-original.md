# 0014. HEIC 保留原件，另存 JPEG 展示副本

日期：2026-08-18
状态：已采纳

## 背景

iPhone 默认拍照格式是 HEIC，而浏览器对它的支持极不一致——Safari 能显示，Chrome 与 Firefox 在多数平台上不能。上传后直接引用原文件，一半用户看到的是裂图。

（本 ADR 原先还捆了「独立深度思考模型」那半，两件事毫不相干；深度思考已拆到 [0015](0015-deep-thinking-tools-and-trace.md)，其中的结论也已被推翻重定。）

## 决策

**上传的 HEIC 转出一份 JPEG 展示副本，同时保留原件。** 数据库记录原件的文件名、MIME 与大小；正文只引用 JPEG。导出、备份、孤儿清理与彻底删除四条链路同时处理两类文件。

## 备选方案与否决理由

1. **只存 JPEG，丢掉原件**：省一半磁盘，但 HEIC 的动态范围与元数据不可逆地损失了。图片是笔记内容的一部分，用户拖进来的那份就是他要保存的东西，应用无权替他做有损转换。
2. **只存 HEIC，前端按需解码**：需要在浏览器里塞一个 WASM 解码器，首屏体积与解码耗时都不划算，且离线壳（[0006](0006-pwa-offline-shell.md)）会跟着变重。
3. **依赖浏览器原生支持**：实测不成立，这正是问题本身。

## 后果

- 磁盘占用约翻倍（原件 + 副本），单用户本地部署可接受。
- 四条链路都要成对处理，漏掉任一条就会留下孤儿：导出缺原件、备份不完整、清扫删不干净。验收清单见[图片与深度思考测试指南](../图片与深度思考测试指南.md)。
- 转换失败（如像素数超限）时整个上传失败并给出中文错误，不留半成品记录。
