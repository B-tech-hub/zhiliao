# 0007. 回收站采用软删除，不做版本历史

日期：2026-08-14

状态：已采纳

## 背景

v0.1 的删除是物理删除，误删不可恢复——对「数据信任」主题这是首要缺口。恢复能力有两条路线：软删除（删除标记 + 保留期）或版本历史（每次修改留快照，删除只是一种版本）。同时探索发现物理删除一直遗留孤儿数据：图片文件与 `images` 记录、note 级 AI 会话都不随笔记删除清理；且 `images.noteId`「保存时回填」从未实现，孤儿判定无法依赖归属字段。

## 决策

**软删除**：`notes.deleted_at` 置位即入回收站（局部索引只覆盖已删行），30 天后随每日清扫物理删除。否决版本历史：单用户随手记场景的误删痛点是「整条找回」而非「改坏回滚」，版本历史的存储、UI 与合并复杂度对本项目收益不成比例；每日备份（保留 7 份）已兜底「改坏」场景。

四个非显然子决策：

1. **保留期固定 30 天，不可配置**——单用户产品少一个配置项胜过多一分灵活。
2. **清扫只挂在每日备份成功之后**（`startDailyBackup` 的定时回调内，`doBackup()` resolve 后执行）：被清数据必然存在于刚完成的当天备份中，构成最后一道找回渠道；备份失败当天不清扫（无快照不销毁）；手动「立即备份」不触发清扫，保持其语义纯粹。推论：彻底删除的数据在既有备份中最多再保留 7 天（备份轮转）。
3. **孤儿图片以全库正文引用为准绳判定**（`extractImageFilenames` 扫描全部笔记，含回收站——可恢复笔记的引用绝不能删），不依赖从未落地的 `noteId` 回填；附 **24 小时上传宽限期**——图片先入库、正文 2 秒防抖后才保存，无宽限期会误删「正在编辑尚未保存」的笔记里的图。全局扫描顺路还清 v0.1 物理删除欠下的历史孤儿（图片与 scope 失效的 AI 会话）。
4. **删除主题时回收站笔记一并回落未分类**（回落 UPDATE 不过滤 `deleted_at`）：`PRAGMA foreign_keys=ON` 下保留旧 `topic_id` 会让删除主题直接违反外键约束，别无选择；副产品是 `topicId` 恒指向存活主题，恢复逻辑零特判。

## 配套改造（实现约束）

- 移入回收站 = 置位 + 删 FTS 行 + 删该笔记 AI 任务；恢复 = 清位 + 重建 FTS + 被打断的 AI 整理（pending/processing）重新入队。
- 全部读路径加 `deleted_at IS NULL` 过滤（列表/详情/搜索回表与 LIKE 降级/主题计数/批量移动/建议采纳/AI 取样与计数/对话上下文）。
- `rebuildFtsIfNeeded` 判据改为「未删除笔记数 == FTS 行数」——沿用全量计数会因回收站笔记不在 FTS 而恒等式永久破缺，每次启动都全量重建。
- LLM 在途竞态：AI 调用期间笔记可能入回收站，回写前重读需带过滤，命中即放弃回写（processNote 与 markNoteFailed 两条路径）。

## 备选方案与否决理由

1. **版本历史**：见上，复杂度不匹配痛点。远期若做块编辑器可重新评估。
2. **逐笔追踪引用的局部孤儿清理**（彻底删除时只清「该笔记引用且无他人引用」的图片）：需要两套引用判定，且历史欠账永远还不上。全库扫描在单用户量级毫秒级完成，一套逻辑通吃。否决局部方案。
3. **回收站进底部导航**：低频功能不值一级入口（移动端 Tab 已满 4 个）；参考 Bear/flomo 放二级——设置 → 数据。

## 后果

- 新增迁移 `0005_soft_delete`、`src/lib/trash.ts`、`/trash` 页面、`POST /api/trash/restore|purge`；删除类 API 语义变更（详情页对已删笔记 404）。
- 升级兼容：旧库迁移后全部 `deleted_at = NULL`，FTS 判据恒等式天然成立，不触发误重建。
- 验收项见 `tests/lib/trash.test.ts`（软删/恢复/彻底删除/孤儿三保护/30 天边界）与 `tests/lib/search.test.ts`、`tests/lib/process-note.test.ts` 的回归用例。
