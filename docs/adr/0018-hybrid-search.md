# ADR 0018：混合检索与 Embedding 存储

## 状态

已采纳（2026-08-22）。

## 决策

- 保留 jieba + SQLite FTS5 BM25，多词查询使用 OR 召回并按命中词数加权。
- 语义检索使用云端 OpenAI 兼容 `/embeddings` 接口，`EMBEDDING_BASE_URL`、`EMBEDDING_API_KEY`、`EMBEDDING_MODEL` 三项必须齐全，不继承聊天模型配置。
- 向量存入 `notes.embedding` BLOB，模型标识、维度和更新时间分别落库。应用层扫描计算余弦相似度，不引入 sqlite-vec native 扩展。
- BM25 与向量结果使用 RRF（k=60）融合，不在本轮使用 LLM 重排。
- 当前配置模型与落库模型不一致的向量不参与余弦计算；搜索保留 BM25，并提示可在设置页补算。
- 模型名与维度**同时**对上才参与计算。只比模型名不够：供应商调整同名模型的默认输出维度时，那批向量会被静默排除，用户既搜不到又看不到提示。维度不符与算不出相似度（零向量、字节数不符）一并计入提示条数。
- 笔记向量在 AI 整理归档后才入队（整理会推进 `updated_at`，旧向量自然失效重算）；仅在未配置文本模型、压根不会走整理链路时才于保存时直接入队，避免每条笔记先用无标题正文白算一次必被覆盖的向量。
- 单条输入截断到 5000 字：多数 embedding 模型上限 8192 token，中文按 1 字≈1.5 token 估算。超限供应商直接回 400，没有降级余地。

## 后果

未配置 Embedding 或供应商暂时不可用时，搜索继续使用 BM25（供应商失败会记 `console.warn`，避免静默降级被误认为语义检索正常工作）。个人量级全表扫描可接受，换模型不需要重建数据库表；万条以上笔记若实测延迟过高，再增加预筛选或专用索引。

「不回落」这条语义必须在设置页明示，光写进文档不够：实测中出现过只填模型名、baseUrl 静默兜底到环境变量里另一个服务的情况——页面一切正常，向量却由别处产出，且落库的 `embedding_model` 记的是用户填的名字而非真实产出方。因此设置页需显示每项的配置来源与**当前生效的接入点原值**，并在三项不齐时明确标注「未启用」。这也是维度校验必须存在的另一个理由：模型名不可信时，维度是唯一还能自证的凭据。

长笔记的单一向量会稀释语义、末尾内容召回率偏低，分块（chunking）是后续独立议题。
