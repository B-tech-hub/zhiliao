# 0003. AI 对话上下文采用直接注入而非全库 RAG

日期：2026-08-11
状态：部分被 [0008](0008-assistant-tool-calling.md) 取代

> **被取代的是作用域前提**：v0.3 起 AI 对话升级为全局助手，不再「围绕当前笔记或主题」展开，当前笔记/主题降级为可摘除的上下文附件，助手可通过 `search_notes` 工具检索全库。
>
> **未被取代的部分仍然有效**：不建向量索引、不做 RAG 的结论保持不变——`search_notes` 走的是本文所说的 FTS 关键词检索；双模型配置（文本 + 视觉）也照旧。详见 [0008](0008-assistant-tool-calling.md)。


## 背景

需要为知识库加入 AI 对话能力（参考 NotebookLM）。对话如何"看到"笔记内容有两条路：把相关内容直接塞进 prompt，或建向量索引做全库检索增强（RAG）。

## 决策

对话**围绕当前笔记或主题**展开：

- 笔记作用域：注入标题 + 正文全文；
- 主题作用域：注入主题名 + 该主题下所有笔记的标题与摘要列表；
- 上下文超过上限（12000 字符）时截断，并在 system prompt 中告知模型。

不建向量索引，不做全库检索。同时采用**双模型配置**：文本对话用现有 LLM 配置，AI 读图走独立的视觉模型配置（`vision_*` 三键，缺省项回落文本模型配置）。

## 备选方案与否决理由

1. **全库 RAG（向量检索）**：需要嵌入模型、向量存储、切片策略与同步管道，复杂度数倍于当前需求；个人库规模下"当前主题/笔记"作用域已覆盖绝大多数提问场景。暂缓，非否决——将来可在此基础上扩展。
2. **复用 FTS 关键词检索做轻量 RAG**：召回质量依赖用户问题的用词与笔记一致，中文口语化提问命中率差。暂缓。

## 后果

- 对话历史持久化到 `conversations` / `messages` 表，按 `(scope_type, scope_id)` 归属。
- 回答走 SSE 流式（`/api/chat`），assistant 消息在流结束时一次性落库，避免 better-sqlite3 逐 token 同步写阻塞事件循环。
- 大主题下笔记很多时上下文会被截断，回答可能不完整——这是可接受的已知限制。
