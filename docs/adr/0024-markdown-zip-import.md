# ADR 0024：Markdown zip 反向导入

状态：已接受（2026-08-27）

## 背景

ADR 0020 建立的增量 Markdown 导出是**只出不进**的：笔记持续写成 `data/notes/<主题>/<标题>-<id>.md`，但没有任何路径能把它们吃回来。设置页的「导出全部数据」同样只有一个方向。

这在两个场景下会真正咬人：一是从 Obsidian / flomo / Memos 迁移过来的用户，手上有几百篇现成笔记却只能一条条粘贴；二是从备份 zip 里挑几条恢复——现有的备份恢复是整库覆盖（见 `docs/备份与恢复.md`），粒度太粗。

`export.ts` 里那行注释写在前面：front-matter 之所以带 `id`，就是**「为将来反向导入的去重铺路」**。这份 ADR 把那条路铺完。

## 决策

1. **首版只吃自家导出的 zip**，外来格式（Obsidian 的 `![[wiki 嵌入]]`、flomo/Memos 的各家 front-matter）留到下一轮。理由是验收手段：自家格式可以用「导出 → 导入 → 逐字段比对」自证互为逆运算，外来格式没有这种自证，只能靠一堆手造样本。骨架与全部安全风险都在这一版里解决，第二版只是在稳定骨架上加解析分支。

2. **导入默认不跑 AI 整理**，界面上是一个默认不勾的开关。标题、主题、标签、摘要一律取 front-matter 与目录名。导入 500 条若各触发一次 `processNote`，就是 500 次主力模型调用——这正是意图文档批评过的「每条笔记必调一次主力模型」在导入侧原样重演。

3. **不跑整理时 `ai_status` 必须写 `skipped`，不能留 `pending`。** `trash.ts` 的每日清扫会把 `pending`/`processing` 的笔记当作「中断的任务」重新入队。留 `pending` 等于给成本炸弹开了后门：用户明明没勾选，几百条笔记会在当晚自己跑起来。沿用 `weekly-review.ts` 给自己生成的笔记标 `skipped` 的既有约定。

4. **front-matter 里带了的字段视为用户已定，落库即置锁**（`title_locked` / `topic_locked` / `tags_locked`）。没带的留 0，将来手动「重新处理」时 AI 还能补。这条让第 2 条与 AI 流水线自洽：即使勾了整理，AI 也只补空缺，不会改掉来源里已有的标题。

5. **同 id 已存在时默认跳过，可选覆盖。** 判重刻意**不排除回收站**——同 id 的笔记躺在回收站里也算已存在，否则跳过判定会漏掉它、而覆盖模式会撞主键。覆盖时把 `deleted_at` 一并清空（用户明确要覆盖，就该把它捞回来），并清空向量五列、删掉全部分块：正文已经换了，旧向量必然对不上。

6. **部分失败不整体回滚。** 逐条独立处理，失败与跳过各自记进报告，最后返回 `{imported, overwritten, skipped[], failed[], images, topicsCreated[]}`。对一个几百条的包，全有全无比部分成功更难用。

7. **zip 是不可信输入，校验挡在 `import.ts` 这一层**，下游的 `saveImage` / `writeImportedNote` 只负责写不负责防。条目名拒绝绝对路径、盘符、`..` 段、反斜杠与控制字符；条目数上限 5000、解压总量 500 MB、单篇 Markdown 2 MB、单张图片 20 MB（与上传一致）；请求体上限 200 MB。**路径穿越整包拒绝，不做「跳过这条继续」**——正常导出不会产生这种条目，出现即视为构造过的包。

8. **写入复用既有的唯一入口**：笔记走 `note-write.ts` 新增的 `writeImportedNote`（与 `createNote` 并列，共用 FTS 同步 / 锁字段 / 入队 / 增量导出这四件收尾），图片走 `uploads.ts` 的 `saveImage`。两个文件的头部注释都写着「唯一入口，另开一条的代价是某某会漏掉它」，导入没有资格例外。

9. **HEIC 原件靠文件名主干与展示副本配对。** 导出时 `assets/a.jpg` 与 `assets/originals/a.heic` 共用 id 作主干，导入据此配回一对，交给 `saveImage` 新增的 `original` 参数成对落库。

10. **请求体直接是 zip 原始字节，不套 multipart。** 边收边落临时文件，选项走查询串。

11. **先解析全部 Markdown、定下哪些笔记真会写入，再去解压它们引用到的图。** 反过来（先存图后写笔记）在重复导入时会一次次复制全部图片。包里没有任何笔记引用的图不导入——它没有可归属的笔记，落盘即孤儿。

## 取舍

**第 1 条的代价是用户当下最想要的那个功能（从 Obsidian 搬家）还没到手。** 接受它，是因为往返自证这个验收手段的价值高得不成比例——它一次性覆盖了 front-matter 解析、时间戳还原、标签映射、主题创建、图片回写这五条链路，而且不需要任何手造样本。第二版加解析分支时，这个测试仍然守在那里。

**第 3 条是本次最接近事故的一处。** 它不是导入模块自己的问题，而是导入与一条既有的、写在别处的清扫逻辑之间的耦合。如果只盯着导入模块本身写测试，这个后门不会被发现；它是在通读 `aiStatus` 的全部使用点时抓到的。已固化为断言。

**第 7 条选择「整包拒绝」而非「跳过非法条目」**，是因为这两种处理对应两种完全不同的判断：脏数据应当跳过，攻击信号应当拒绝。路径穿越属于后者。代价是一个被别的工具重打过包、恰好带了怪路径的正常 zip 会被整个拒掉，用报错文案点明是哪一条来缓解。

**没有做的一件事**：`api/uploads/route.ts` 的 HEIC 分支仍然是直接 `insert(images)`，没有改用第 9 条新增的 `saveImage(original)`，尽管这正是 `uploads.ts` 头部注释警告的重复路径。它没有路由级测试覆盖，而 HEIC 是 ADR 0014 踩过坑的地方，此刻合并的收益不抵风险。**这是一笔明账，记在这里等一个有测试托底的时机。**

## 后果

导出与导入自此互为逆运算，`data/` 目录里的 Markdown 不再是单向的副本，而是一种可以走回来的中间格式。

对「取用能力收尾计划」的直接影响：T2/T3/T4 全部卡在「正式库只有 7 条测试笔记，候选池太小」上（见该文 §5、§6）。导入是把真实笔记搬进来的唯一批量路径，因而是解锁那三项评估的前提，而不是与它们并列的第四项功能。

**第 11 条是真实往返验收抓到的，30 条单元测试一条也没覆盖它。** 最初的实现是「先存图，再写笔记」——因为正文要拿到新 URL 才能改写引用，这个顺序看上去是被逼出来的。在隔离实例上把同一个包导第二遍时，两条笔记都正确跳过了，但报告里赫然写着「图片 1 张」：那张图被重新解压、重新落盘、重新写进 `images` 表，而没有任何笔记引用它。它要等孤儿清扫过了 24 小时宽限期才会被回收，期间每导一次就多一份。真正的修复不是补一次清理，而是把顺序倒过来——**判重本来就可以在解压图片之前完成**，被逼出来的只是「写笔记」与「存图」的先后，不包括「判重」。这条印证了开发日志里那句元教训在写入路径上同样成立：**单元测试能证明每一步都对，证明不了这些步骤的排列是对的。**

一处尚未验证的：往返测试用的是两条笔记加一张图的小包，条目数上限 5000、解压 500 MB 这两条边界只有构造测试覆盖，没有在真实规模的包上跑过。真正的大包导入会在用户第一次搬家时才发生。
