## 背景

排期补充（2026-09-13）：已批准[开源发布优先范围调整](../../_bmad-output/planning-artifacts/sprint-change-proposal-2026-09-12-open-source-first.md)，公网工作后移。本文架构决策与技术要求保持；现有本机证据不替代硬配额、实际正式服务、HTTPS、补丁镜像与最终启动路径验收，不因排期变化修改 Story 完成状态。

Story 2.2 最初让 app 与 mockllm 只加入 `internal: true` 网络，并由 app 声明宿主机端口。2026-09-10 在 Docker Engine 28.4.0 上发现三个实际问题：入口端口没有发布；业务容器仍能访问监听网桥网关的宿主机对照服务；Next.js 中间件不能在正文未收完时提前拒绝超大长度声明。静态 Compose 解析与中间件单元测试不足以证明这些运行边界。

用户已批准改用三容器拓扑，保留宿主机 3210 入口及三个 Demo 命名卷。该工作属于现有 Demo 的部署隔离，不扩展产品能力。

## 决策

| 服务 | 网络 | 宿主机入口 | 数据与凭据 |
|---|---|---|---|
| ingress | `ingress_net`、`demo_net` | 默认 `127.0.0.1:3210:8080` | 只读 Nginx 配置；无业务卷、模型密钥或会话密钥 |
| app | 仅 `demo_net` | 不发布 | 独立 `demo_db`、`demo_uploads`、`demo_notes`；独立 Demo 密钥 |
| mockllm | 仅 `demo_net` | 不发布 | 无业务卷和真实模型凭据 |

1. Nginx 使用固定版本和摘要，监听非特权端口 8080，仅转发到 `app:3000`。入口采用非 root、只读文件系统、移除 capabilities，并设置 CPU、内存、进程数、临时目录和日志上限。
2. `demo_net` 同时设置 `internal: true` 和 `com.docker.network.bridge.gateway_mode_ipv4: isolated`，不分配宿主机网桥网关。网络和卷名随 Compose project 派生。
3. Nginx 使用 `client_max_body_size 200m` 限制实际请求体，关闭请求和响应缓冲，保留 SSE。接收正文空闲时限为 30 秒；代理读写空闲时限为 300 秒。中间件长度检查继续作为补充。
4. 入口用 `$remote_addr` 重建 `X-Forwarded-For`，避免客户端通过伪造首个地址绕过登录限流。目标 HTTPS 入口的地址信任链另在部署时验证。
5. mockllm 健康后启动 app，app 健康后启动 ingress。app 健康探针使用候选镜像已有的 Node.js。

app 与 ingress 共用业务内网，因此 app 可以访问 `ingress:8080`。这是已批准的网络例外；入口只能转发到 app，不提供任意目标代理，也不能因此放宽 app/mockllm 到宿主机、正式网络或外部模型的访问。

## 备选方案与取舍

- 仅使用 `internal: true`：已由宿主机对照服务证明隔离不足。
- 将 app 接入普通入口网：能发布端口，但扩大持有业务数据容器的出站范围。
- 仅依赖中间件和 `Content-Length`：不能在 Next.js 接收正文之前承担入口限额。

增加 Nginx 带来一个额外镜像和配置维护点；isolated 模式与业务卷配额还依赖目标 Docker/存储环境。维护者应沿用 [Demo 部署隔离验收](../Demo部署隔离验收-2026-09-10.md) 的证据分层和剩余门槛，不能将本机成功或配置解析成功等同于公网可发布。
