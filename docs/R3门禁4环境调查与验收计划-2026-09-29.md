## 4. 调查时的发布链缺口

本节保留实施前的调查事实。P 阶段现已去除缓存恢复，增加原生架构、manifest 和匿名安装检查；真实环境是否通过仍须 V/R 的运行证据。

| 文件或行为 | 已有能力 | 门禁 4 尚缺 |
|---|---|---|
| `.github/workflows/release.yml` | amd64 用 `ubuntu-latest`，arm64 用 `ubuntu-24.04-arm` 原生构建 | runner 实际架构、平台运行结果及安装取用证据 |
| Release 缓存配置 | `cache-from/cache-to: type=gha`，校验依赖也配置 npm cache | 不满足本轮无缓存声明，需独立无缓存路径 |
| Release 触发 | 推送 `v*.*.*` 后推送 GHCR digest、合并标签并创建 Release | 不能作为只读调查或无发布预检入口 |
| manifest 检查 | `imagetools inspect` 输出清单 | 没有对两种运行架构、对应子 digest 和 revision 的硬断言 |
| `.github/workflows/ci.yml` | main push / PR 上执行四条完整门禁 | PR 推送会触发重验证，不能把普通分支推送视为没有运行副作用 |

Release 文件注释允许 arm runner 排队时删去 arm64 临时单架构发布，这与当前 R3 门禁 4 明确要求双架构不一致。采用当前发布清单的要求：arm64 不可用就保留未通过，不降成单架构；准备阶段同步修正这条注释及相应硬检查。

### R：一次 RC 构建完成无缓存、双架构与分发，另行确认发布操作

V 通过并审阅发布材料后，按现有维护者流程准备最终提交与 RC tag。推送/合并 main、推送 `v0.6.1-rc1`、GHCR 写入和 GitHub 预发布 Release 都是具体外部动作，须另行确认。门禁 4 的真实 registry 分发与 RC 流程有依赖，因此不能要求“全部门禁 4 先通过，才允许生成第一个 RC”。执行前复查目标 tag 未被占用；发现占用就停止，不覆盖旧 tag。

1. 先完成进入 RC 前的 CHANGELOG 标题/日期和共用 Release Notes 定稿，再锁定最终提交；不要在 RC 验完后为改日期插入新的发布源码提交。
2. 在两种原生 runner 各构建一次，按 amd64 → arm64 顺序；记录 tag → commit → 各平台 digest。每个平台从干净 checkout 开始，不复制本机 `node_modules`、`.next`、`next-env.d.ts`、env 或数据。npm 使用专用空缓存，不恢复 Actions/npm cache；Docker 不导入 GHA/本机构建缓存，使用 `--no-cache --pull`，记录 builder 初态、基础镜像 digest、系统和 Node 版本。源码获取、npm 安装、构建分别计时；不把客户端空缓存扩大解释为远端 CDN 无缓存。
3. 合并真实 GHCR OCI 索引，保存原始 JSON 和 SHA-256。严格断言运行镜像包含 `linux/amd64`、`linux/arm64`，子 digest 与两次构建对应，OCI revision 与最终提交一致；attestation 描述符单列，不能误当成第三种运行平台或忽略缺失架构。
4. 在独立的原生 runner/空 Docker 存储中匿名拉取固定 RC 引用并核对 digest，记录拉取前镜像/层缓存状态、耗时、清单及平台选择。使用刚构建的本地镜像运行不能替代此项。
5. 两平台运行同一最小安装矩阵：系统架构与 Node `process.arch` 一致，SQLite 写读、中文分词、Sharp 图片处理、健康检查、登录、合成笔记保存/检索通过；记录 MCP 握手版本 `0.6.1` 和重建后的笔记/图片/Markdown 持久化。成功结果可供门禁 5 按完全相同身份复用，不能自动关闭门禁 5 的异地恢复或全部 RC 验收。

仅用合成数据，无真实模型调用，绑定回环入口和独立卷，应用环境不透传宿主模型配置。失败保留脱敏日志；只清理本次带标识的资源。建议每个平台构建 job 最长 60 分钟、安装 job 最长 15 分钟；两个架构顺序执行，首次失败不自动循环重跑。配额和时限在启动前确认，不自动启用付费资源。镜像按 digest 推送在安装检查之前发生，失败时可能留下远端 digest/RC tag；记录失败并停止，不自动删除或覆盖远端产物。

RC 与正式 tag 必须指向同一完整提交；正式发布仍属于门禁 6。普通安装入口继续固定 v0.6.0，直到 0.6.1 实际可获取且对应验收完成。

## 6. 验收矩阵与退出条件

| 验收项 | 输入与动作 | 必须保存的结果 |
|---|---|---|
| 身份复现 | 固定完整提交，全新 checkout、独立生成声明 | Git SHA/tree、应用/依赖/配置哈希；`next-env.d.ts` 无本机旧路径 |
| 无缓存 | 空 npm cache、不恢复构建缓存，实际安装及构建 | 缓存初态、命令、退出码、耗时、基础镜像 digest、平台/工具版本 |
| 原生双架构 | 分别在 x86_64/aarch64 Linux 构建并运行 | 两份平台日志和原生模块实际行为，不以 Buildx 平台列表代替 |
| 分发与 manifest | 真实 RC 索引及独立客户端匿名获取 | RC tag、索引与子 digest、架构/revision 硬断言、拉取证据 |
| 最小安装 | 无模型、合成数据、独立卷 | 健康/登录/记录/检索、图片、Markdown、重建持久化、MCP 版本 |
| 清理与诚实结果 | 成功、失败或超时 | 本轮资源清单、脱敏失败日志、清理结果；失败不得记 passed |

全部证据归档到新目录 `docs/验收证据/r3-gate4-061-<run-id>/`，每次运行独立，至少包含 summary、身份、环境、命令日志、平台结果、manifest 和清理记录。只有 V 与 R 对应必需项都有证据，门禁 4 才能关闭；一项不可用即保留该项未验，不改旧失败记录。

## 7. 影响、风险与证据边界
