## 4. 批次 A：#11 Mermaid 性能缺陷

### 4.1 目标

回答两个问题：

1. 问题是否在真实桌面浏览器和生产构建中复现？
2. 若复现，究竟是 Mermaid 自身、TipTap NodeView 更新、主题观察器，还是临时 DOM 清理造成的循环？

### 4.2 已知证据

- 单条笔记、单个两节点图即可触发。
- headless Chrome + swiftshader + `npm run dev` 下 CPU 与内存线性增长。
- 在 #3 前后的提交上表现一致，可排除功能开关改动直接引入回归。
- `src/components/mermaid-code-block.tsx` 中存在三个高价值假设：
  - `mermaid.render()` 的临时 DOM 仅在异常分支显式清理。
  - `MutationObserver` 对根元素 `class` 的变化强制重渲染，并绕过去重判断。
  - NodeView `update()`、异步渲染完成后的 `applyMode()` 可能形成重复更新。

### 4.3 复现矩阵

使用同一份隔离数据、同一个 Mermaid 代码块，按以下顺序执行。每轮最多观察 5 分钟，发现线性失控立即终止标签页，不做长时间放任。

| 构建 | 浏览器 | 图形环境 | 目的 |
|---|---|---|---|
| dev | 真实 Chrome/Edge | 硬件加速 | 判断日常开发是否复现 |
| production | 真实 Chrome/Edge | 硬件加速 | 决定是否阻塞发布 |
| production | headless Chrome | 默认 headless 图形栈 | 判断是否为 headless 特有 |
| 最小 HTML | 真实浏览器 | 直接调用 `mermaid.render` | 区分 Mermaid 与 TipTap 集成问题 |

每轮记录：

- 浏览器版本、Node.js 版本、构建模式、是否硬件加速。
- 首次渲染次数、30 秒和 5 分钟的 CPU/内存。
- 页面中 Mermaid 临时节点数量。
- 根元素 `class` 变更次数。
- NodeView `update()`、`renderDiagram()`、`applyMode()` 调用次数。

### 4.4 决策规则

- **生产构建 + 真实浏览器复现**：视为发布阻塞缺陷，完成修复后再进入 #6。
- **仅 dev 模式复现**：继续定位开发模式触发条件；若生产稳定，在 #11 写清边界并降低发布阻塞级别。
- **仅 headless/软件渲染复现**：建立最小复现并记录测试环境限制；不为了 headless 特性盲改生产路径。
- **任何环境都无法复现**：保留原始数据和版本信息，在 Issue 中记录无法复现条件，移除 `needs-info` 前先补齐人工真实浏览器结论。

### 4.5 修复策略候选

仅在证据命中后采用对应改动，不一次性把所有假设都改掉：

1. 无论成功或失败，都在 `finally` 清理 Mermaid 为本次渲染创建的临时 DOM。
2. 主题观察器记录上一次解析后的主题，只在 `dark` 与 `neutral` 真正变化时重渲染。
3. 不以 `force=true` 无条件绕过去重；主题未变且源码未变时必须直接返回。
4. 对并发渲染保留版本号取消机制，旧 Promise 完成后不得覆盖新结果。
5. 若 `mermaid.initialize()` 被证明参与循环，改为受控初始化，不在每次普通更新时重复执行。
6. 若问题来自 NodeView DOM 更新，缩小 `applyMode()` 的变更范围，避免对 ProseMirror 观察范围制造无意义 mutation。

### 4.6 验证与文档

局部验证优先：

- 为去重、主题变化、销毁后异步返回、临时 DOM 清理补组件或 DOM 单元测试。
- 使用一个合法图和一个非法图验证成功、失败、源码回退、明暗切换。
- 生产构建真实浏览器观察 5 分钟：预热后内存不再线性增长，CPU 回落到空闲水平，渲染次数稳定。
- 验证编辑源码、点击图回到源码、保存后 Markdown 围栏不变。

文档同步：

- 若确认并修复，在 `CHANGELOG.md` v0.6.0 修复项中补充。
- 在 `docs/开发日志.md` 记录根因、误导性假设与真实性能基线。
- 只有形成新的长期架构约束时才新增 ADR；普通内存泄漏修复不需要为了留痕硬写 ADR。
- 在 #11 评论中附复现矩阵和修复前后数据，再关闭 Issue。

## 6. 共享基础设施决策

本节公网域名、服务器与存储决策仅阻塞后续 #5，不再阻塞本地演示、文章/安装分发或免费自托管试用。#4 按真实使用者自有设备与 HTTPS 路径验收，不能用公网后移免除手机要求。

#4 与 #5 可以共用一台常驻机器，但不能共用安全边界。推荐拓扑：

```text
手机快捷指令
  → Tailscale HTTPS
  → zhiliao-prod（真实配置、真实数据，仅私网）

公网访客
  → 公网域名与 HTTPS 反向代理
  → zhiliao-demo（mock LLM、演示数据、受限权限、定时重置）
```

### 6.1 必须由维护者确定的事项

- 正式实例运行位置：家中常开设备、NAS 或云服务器。
- 手机主平台：iOS 快捷指令或 Android 等价工具。首轮只要求一个主平台完整验收。
- 公网 demo 使用的域名、DNS 与服务器。
- 是否让正式实例与 demo 共机。若共机，必须使用独立 compose project、网络、卷和环境文件。

### 6.2 推荐隔离规则

- 正式项目名固定为 `zhiliao-prod`，demo 固定为 `zhiliao-demo`。
- demo 不挂载正式目录，不读取正式 `.env`，不共享 Docker volume。
- 正式实例只经 Tailscale 暴露，不向公网开放登录页。
- 公网反向代理只转发 demo 容器。
- demo 容器禁止访问云元数据地址和内网网段，能做出站白名单时只允许必要依赖。
- 为 demo 设置 CPU、内存、磁盘和请求体上限，避免公开上传接口耗尽宿主机。

## 7. 批次 C：#4 手机一键记录

### 7.1 目标与范围

从手机主屏、控制中心或分享菜单一步写入正式库，并走完现有 AI 整理队列。首期不改服务端接口：

```http
POST /api/external/capture
Authorization: Bearer <capture:write token>
Content-Type: application/json

{
  "content": "要记录的内容",
  "topicId": "可选主题 ID"
}
```

成功响应为 HTTP 201；空内容返回 400；Token 无效或权限不符返回 401。

### 7.2 实施步骤

1. 完成 v0.6.0 发布并升级正式实例。
2. 通过现有 Tailscale 手册让正式实例在蜂窝网络下也可使用 HTTPS 访问。
3. 在设置页创建一个专用 `capture:write` Token，不复用 `knowledge:read` Token。
4. 制作「分享文本」入口：接收系统分享的文本或网址，组装 JSON 后调用捕获接口。
5. 制作「语音听写」入口：先听写，再让用户快速确认文本，随后发送。
6. 对 201、400、401、超时和网络断开给出明确通知，失败时保留原文本以便重试。
7. 在设置页吊销 Token，确认旧快捷指令立即返回 401；再生成新 Token 更新快捷指令。
8. 检查写入后的笔记进入 AI 队列，最终得到标题、标签、摘要和主题。
9. 开始连续 7 天真实使用观察，不以测试笔记充数。

### 7.3 快捷指令安全要求

- Token 只保存在快捷指令本地，不写入截图、README、日志和共享模板。
- 对外发布的模板必须使用占位符，导入后由用户自行粘贴 Token 和实例地址。
- 正式 Token 只授予 `capture:write`，即使泄露也不能读取知识库。
- 文档明确说明 Token 丢失无法找回，只能吊销后重建。
- 分享网址时默认记录 URL 与用户选中文本，不在快捷指令里增加未经讨论的网页抓取能力。

### 7.4 文档交付

建议新增 `docs/手机快捷记录.md`，并从 README、README.en.md 和文档索引链接。内容至少包括：

- 正式实例 HTTPS 前置条件。
- Token 创建与吊销步骤。
- iOS 或 Android 主平台的逐步配置图文。
- 可导入模板或官方分享链接。
- 接口请求和错误码。
- 常见故障：401、超时、证书不受信任、蜂窝网络不可达、AI 一直待整理。

若接口契约因此变化，必须同步 ADR 0019 和接口文档；若只增加客户端模板，不改 ADR。

### 7.5 验收

- 手机主屏或控制中心一步进入记录流程，不先打开浏览器登录。
- 分享文本和语音听写两种入口均成功。
- 仅使用蜂窝数据时成功写入。
- Token 吊销后立即失效。
- 写入内容走完 AI 整理。
- 连续 7 天每天至少一条真实笔记来自该入口。

若技术项全部通过但 7 天行为信号失败，不关闭 #4。重新做五问溯因，判断摩擦来自入口层级、听写确认、网络等待、内容组织焦虑或其他环节。

## 8. 批次 D：#5 公网 demo

当前后移，原 §8.5 公网验收完整保留。重启前按 Story 2.2 核对目标环境、资源与配额、实际正式服务隔离、HTTPS/入口信任链、补丁镜像和最终启动路径；2.2 全部原验收与审查通过后才进入 2.3，重置/恢复通过后才开放入口。

### 8.1 上线前安全缺口

以下是已发布 v0.6.0 的原安全缺口，不代表当前源码尚未实现服务端保护。该旧镜像的 `DEMO_MODE` 主要做空库播种与登录页密码提示，不能直接视为公网沙箱；共享密码登录后，访客仍可能：

- 修改 LLM、Embedding、视觉、推理或图像模型配置。
- 创建 `capture:write` 或 `knowledge:read` Token。
- 上传图片，占用磁盘。
- 修改或删除演示数据，使后续访客看到失真状态。
- 触发备份、导入、重算等高成本操作。

因此，公网部署前需要一个小型「demo 安全化」子任务。它属于部署安全与既有功能保护，不视为冻结中的新功能。

### 8.2 服务端 demo 边界

建议在服务端统一识别公开演示模式，并至少执行：

1. 禁止保存或清除任何外部模型配置，demo 永远只使用容器内 mock LLM。
2. 禁止创建外部 API Token，避免访客获得长期写入或读取入口。
3. 禁止备份下载、数据导入、向量补算等不属于演示主线的操作。
4. 评估是否完全禁止图片上传；若保留，降低单文件上限并配合代理层总请求体限制。
5. 保留新建普通文本笔记、AI 自动归档和主题建议采纳，因为它们是验收主路径。
6. 前端隐藏已被服务端禁止的设置入口，但不能只依赖隐藏按钮。
7. 为被禁止的 API 增加 demo 模式测试，直接请求时返回明确的 403。

### 8.3 部署与运维

1. 使用另行发布、含 Story 2.1/2.2 补丁的新固定版本镜像与 digest；v0.6.0 只作历史基线，避免 `latest` 漂移。
2. 使用独立命名卷和独立容器网络，不挂正式数据目录。
3. 配置域名与 HTTPS，HTTP 自动跳转 HTTPS。
4. 代理层增加请求速率限制、请求体限制和基本恶意流量防护。
5. 容器配置 CPU、内存与日志轮转上限。
6. 设定定时重置，例如每天凌晨销毁 demo 卷并重建，让播种逻辑恢复标准数据。
7. 重置后自动执行健康检查和三步主路径冒烟。
8. 配置最小监控：可用性、磁盘、容器重启次数、5xx 比例、证书到期。
9. 保存一份手动重置命令，定时任务失败时可以人工恢复。

### 8.4 README 与文档

- 完整公网验收通过后，README.md 与 README.en.md 徽章下方、正文之前才放 Live Demo 链接和密码；当前优先提供固定版本安装与免费反馈入口。
- 明确说明演示数据会定时重置，不要输入隐私或真实密钥。
- 新增 `docs/公网演示部署.md`，记录拓扑、环境变量、代理、重置、监控、故障恢复和安全限制。
- `docker-compose.demo.yml` 的注释与实际部署方式保持一致。

### 8.5 验收

- 公网 HTTPS 可访问，证书可信。
- 演示容器不持有真实 API Key，访客也无法写入外部模型配置。
- 访客无法创建外部 Token。
- 正式数据、正式卷、正式环境文件与 demo 完全隔离。
- 新建笔记、AI 自动归档、主题建议采纳三步走通。
- 自动重置和手动重置均成功。
- 资源限制与磁盘保护有效。
- README 中英文首屏链接正确。

## 9. 批次 E：#8 「AI 不编造」30 秒演示

### 9.1 演示设计

演示核心不是证明某个通用模型一定会幻觉，而是让访客看到知了的严格接地边界可被复现。

建议分镜：

1. 左侧展示对照助手回答一个知识库里明确不存在的问题。
2. 右侧在知了的来源问答中提出完全相同的问题。
3. 知了明确回答「来源笔记中没有相关内容」。
4. 快速展示来源集，证明答案边界来自已选择的笔记，而非剪辑隐藏。
5. 结尾显示固定 Release、安装教程与本地复现入口，访客可在自己的隔离实例复现。

总时长控制在 20 至 30 秒，不依赖旁白。画面文字必须在 README 常见宽度下可读。

### 9.2 可复现性要求

- 固定并记录演示数据版本、来源笔记列表、问题文本、对照模型名称与日期。
- 问题必须确实不在来源笔记中，可通过文本搜索和人工核对证明。
- 若对照助手当次没有编造，如实更换问题并重新录制，不剪掉不利结果拼接结论。
- 首期在隔离本地实例通过已有导入或播种路径恢复同一套固定数据后连续两次复现；mock 只证明流程，真实模型输出需保留模型、发送范围、预算与完整样本。
- 后续 #5/Epic 2 公网上线前仍须验证自动/人工重置恢复同一套数据与结论，由 Story 3.3 留存联验关联，不把本地结果当公网通过。
- 演示素材不得包含真实个人笔记、真实 Token 或真实 API Key。

### 9.3 产物与同步

- 更新 `docs/演示GIF录制清单.md`，增加严格接地对比演示的分镜和素材清单。
- 生成体积可控的 GIF 或短视频，并提供静态封面和准确的替代文本。
- README.md 与 README.en.md 在「AI 不编造」承诺附近同步展示。
- 若演示依赖新增固定数据，更新 demo 播种脚本和相应测试。

### 9.4 验收

- 30 秒内，无旁白也能理解差异。
- README 首屏附近可直接看到。
- 问题与演示数据被文档化。
- 首期固定版本、固定数据的隔离本地实例中连续两次得到可复核的严格接地回答；失败和不利结果完整留证。
- 对照展示不做误导性剪辑。

本节本地验收调整已获批准，但远程 #8 正文尚未同步。远程仍含“公网 demo 中可以重复得到知了的严格接地回答”时，不能凭本地素材关闭；后续公网联验按上一节保留给 #5/Epic 2 上线验收，不能静默删除承诺。

## 10. 批次 F：#9 ADR 内容分发

### 10.1 发布时机

固定 Release、首篇文章及安装/恢复文档就绪即可准备分发，不再等待公网 Demo。Story 4.2 依赖 4.1 与上述入口；引用视频时追加 3.2/3.3，引用公网链接时仍等待完整 Epic 2 验收。素材只能展示对应已发布版本，外部发布按具体内容确认。

### 10.2 首篇建议主题

优先使用「设置页配置静默覆盖环境变量，导致 4B 模型从未真正生效」作为主线，因为它具备完整故事结构：

1. 表面现象：配置文件明明改了，行为却没有变化。
2. 潜伏原因：数据库配置优先且界面没有暴露覆盖关系。
3. 实际损失：向量按错误模型重算。
4. 为什么普通测试没发现。
5. 修复：让覆盖关系显式可见，并补防复发验证。
6. 方法论：AI 辅助开发中，配置来源优先级必须成为可观察状态。

第二篇再写「验收判据被真实数据推翻」，避免首篇同时塞入过多故事。

### 10.3 写作要求

- 以决策、证据、错误判断和自我推翻为主线，不写成功学式项目介绍。
- 所有关键结论链接到具体 ADR、开发日志、提交或固化测试。
- 清楚区分当时已知、事后发现和仍未知的部分。
- 中文渠道分别适配标题和开头，不机械复制同一版式。
- Hacker News 使用英文摘要与仓库链接，正文可放英文版长文或项目内英文文档。

### 10.4 流量留存计划

GitHub Traffic 不能等一个月后再一次性补采。发文前建立基线，以实际对外发布时间为 T0，随后定期保存；草稿或发布包完成不启动时钟：

| 时间点 | 记录内容 |
|---|---|
| 发布前 | star、watcher、open issue、views、unique visitors、clones、referrers |
| 24 小时 | 同上，记录各渠道首波流量 |
| 7 天 | 同上，判断短期转化 |
| 14 天 | 保存 GitHub 可见窗口内的完整来源快照 |
| 30 天 | star、issue、实际用户反馈与 demo 使用情况；结合已保存快照做结论 |

建议将快照保存为 `docs/分发数据/` 下的日期化 Markdown 或 CSV，字段固定，避免只留截图。

承接数据按实际入口记录安装尝试、免费反馈和失败；无法取得的 README 点击或使用数据写未知，公网未启用时 Demo 使用写未启用，不填零或判失败。

### 10.5 失败条件

沿用 Issue 的预设条件：首篇发出 30 天后，若 star 仍低于 20 且 issue 仍为 0，则不继续用相同形式批量发文。复盘时区分：

- 内容没有曝光。
- 有曝光但标题与开头没有转化。
- 有仓库访问但 demo 或 README 没有承接。
- 有体验但产品本身没有形成使用意愿。

不同原因对应不同动作，不能统一归因成「再多发几篇」。上述阈值只决定是否停止同形式批量发文，不能单独判定产品或商业失败；公网未启用期间按安装/README 承接分析。

## 11. 批次 G：#10 新功能冻结闸门

### 11.1 指标口径

在持续跟踪前先固定「真实笔记数」定义，建议：

- 计入：用户真实撰写、手机捕获、从个人历史资料导入的有效笔记。
- 不计入：demo 数据、自动化测试数据、专门为验收临时创建的样本。
- 每周回顾等自动生成笔记单独记录，不作为捕获能力成功的主要证据。
- 删除进回收站的无效测试笔记不计入。

建议同时记录两个辅助指标：

- `capture:write` 入口带来的真实笔记数。
- 过去 7 天有真实笔记写入的活跃天数。

### 11.2 跟踪节奏

- #4 启用后的前 7 天每日记录一次。
- 之后每周记录一次真实笔记总数和各入口增量。
- 达到 50 条时只做一次体验复盘，不自动解冻功能。
- 达到 100 条后关闭冻结闸门，重新分诊六个候选方向，仍需逐项立 Issue 和排序。

### 11.3 冷启动模式的例外处理

#10 将「冷启动模式」列为最可能提前解冻的方向，但不得直接开发。只有出现以下证据时才提请提前解冻：

- 小库存下的聚类、主题建议或每周回顾持续制造明确困扰。
- 困扰直接影响 #4 的连续使用信号。
- 关闭或隐藏现有能力比继续教育用户成本更低。

满足证据后，在 #10 中先做人工决策，再另开缺陷或体验修复 Issue；不能借「可提前」绕开闸门。

| 技术验收通过但 #4 没形成习惯 | 真实笔记数继续停滞 | 7 天行为验收作为关闭条件，失败重新溯因 |
| 发文后未及时保存 Traffic | 无法判断渠道效果 | 发布前、1 天、7 天、14 天、30 天定点快照 |
| 同时推进过多外向任务 | 发布、部署、写作都半成品 | 严格按批次退出条件推进，一次只开一个主执行批次 |

## 15. 总体验收标准

- v0.6.0 已发布，升级路径、Release Notes 和多架构镜像经过验证。

- 手机快捷记录在蜂窝网络下可用，并连续 7 天产生真实笔记。
- 公网 demo 使用 HTTPS、与正式数据隔离、无法写入外部模型配置或创建 Token、可自动重置。
- 「AI 不编造」演示可在 README 观看，首期本地复现与后续公网重置联验按第 9 节分别留证。
- 至少一篇 ADR 方法论文章投出，渠道数据按时间点留存。
- #10 持续记录真实笔记数，未达到 100 前没有偷偷恢复新功能开发。
