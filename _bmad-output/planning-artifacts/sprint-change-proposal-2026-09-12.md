### 3.2 阶段一：本机收尾

提议的工作是把已有成果形成清晰的阶段归档，不追加本机实现或重复验证。

1. 归档 A2 代理四项、B2 HTTP/SSE 与同轮网络 20 项、清理及局部回归证据；保留每项的镜像、输入、环境和日期。
2. 在规划、Story 的执行说明和相关文档中统一“本机所选范围已验证，原 Story 尚未完成”的口径。
3. 保留 B1 硬配额未满足、实际正式服务未验收、HTTPS/入口信任链未验收、新镜像未发布及完整门禁未完成的清单。
4. 写清公网阶段的责任人、启动输入和退出条件。缺少输入时保持待安排，不用已完成、本机豁免或 N/A 替代。

阶段退出条件：上述材料完整、引用有效、证据适用范围明确，且原 AC、未完成项、状态和历史失败未被改写。该退出条件仅关闭阶段归档工作，不能用于 Story 2.2 或 Epic 2 的完成判定。

现有本机入口约束保留：主 Demo 为 127.0.0.1:3210，临时验收为 127.0.0.1:3322；仅 ingress 发布端口，app/mockllm 只加入 isolated 业务内网。app 到 ingress 的已批准互通例外不扩大为任意出站能力。

### 3.5 数值门槛与证据复用

- Nginx 实际请求体上限保持 200 MiB；读取/发送代理空闲时限保持 300 秒，原 295–330 秒判定范围、450 秒客户端预算、32 MiB 发送场景上限不变。
- A2 的计时前提仍为两段各 20 秒、误差在 1% 内；长心跳超过 300 秒并正常结束。旧失败和环境恢复过程继续留存，不宣称长期时钟修复。
- 网络维持 4 条必要互通、4 个有效正向对照、12 条负向路径的既有本机覆盖；新目标还需实际正式服务范围，不能因服务停止而判隔离成功。
- 当前三服务的 CPU/内存/PID/日志上限保持原配置，不以阶段拆分为由降低。tmpfs、只读根文件系统和容器可写层限制不能代替业务卷硬配额。
- B1 的 512 MiB / 1 GiB / 256 MiB 是三个卷已有的建议容量，不是已生效值。未来必须确认并实际执行持久硬配额；按原建议，两轮完整容量触发累计至少 3.5 GiB 加探针开销，实施方案须限定写入、占用、时限和中止条件。
- 配额必须在应用首次写入前生效；down -v 后重建卷也须重新设限并验证，失败时不得启动应用。这一存储生命周期验证不替代 Story 2.3 的自动重置和运维验收。
- 复用证据先核对输入、镜像、环境和覆盖范围。新镜像、Engine、存储或代理链发生变化时，复验受影响项；无变化时不重复同类重验证。B2 成功不会把 A2 历史失败改为成功。
- 正式合并/发布门禁仍为 npm run check:design、npm run lint、npm test、npm run build，按项目规则说明必要性并确认后运行。本轮不运行。
